# 04 · 状态迁移（有状态对象）

> 对象行为依赖其**当前状态**——同一操作在不同状态下产生不同结果（订单/审批/支付/工单状态机）。bug 几乎都不在正常流转，而在：① 非法转移未被拒绝；② 并发转移冲突；③ 终态泄漏。

## 什么时候用状态迁移

判别信号：被测对象有"状态字段"（status/state/phase），且方法的执行结果取决于该字段当前值。

- 订单：待支付 → 已支付 → 已发货 → 已完成（还有已取消）
- 审批：草稿 → 待审批 → 审批中 → 通过/驳回
- 支付：处理中 → 成功/失败/超时

## 三要素

1. **状态（State）**：对象能处的稳定形态（节点）。
2. **迁移（Transition）**：由某事件/操作触发，从一个状态变到另一个（有向边）。
3. **动作（Action）**：迁移时执行的副作用（发通知、扣库存、记日志）。

## 完整示例：订单状态机

### 步骤 1：画状态图（节点 + 合法边）

```
        pay()              ship()
 待支付 ────────▶ 已支付 ────────▶ 已发货 ────────▶ 已完成
   │                                  │
   │ cancel()            confirmRecv()│
   ▼                                  ▼
 已取消 ◀─────────────────────────────（不可，已发货不能直接取消）
   （终态）
```

### 步骤 2：列出合法迁移（0-覆盖，每条边一个用例）

| # | 起始状态 | 操作 | 期望终态 | 期望动作 |
|---|---|---|---|---|
| 1 | 待支付 | `pay()` | 已支付 | 记录支付时间 |
| 2 | 待支付 | `cancel()` | 已取消 | 释放库存 |
| 3 | 已支付 | `ship()` | 已发货 | 生成物流单 |
| 4 | 已发货 | `confirmRecv()` | 已完成 | 触发售后窗口 |

> 这是 **0-覆盖**（0-switch）：每条合法迁移（每条边）至少走一次，不关注连续多步。

### 步骤 3：列出非法迁移（被拒绝）

| # | 起始状态 | 操作 | 期望 | 防什么 |
|---|---|---|---|---|
| 5 | 已支付 | `pay()` | 抛异常/拒绝 | 防重复支付 |
| 6 | 已取消 | `pay()` | 抛异常 | 防僵尸订单复活 |
| 7 | 已发货 | `cancel()` | 抛异常 | 已发货不能取消（要走退货） |
| 8 | 已完成 | `ship()` | 抛异常 | 防终态泄漏/状态回退 |
| 9 | 已完成 | `confirmRecv()` | 抛异常 | 终态后操作 |

### 步骤 4：终态验证

每个终态（已取消、已完成）额外测：**从终态出发的所有操作都应被拒绝**。这是上表 #6/#8/#9 的归类。

### 步骤 5：落地（映射见 06）

```java
@Test
void should_transitToPaid_when_payFromPending() {
    Order order = new Order(Status.PENDING_PAYMENT);
    order.pay();
    assertEquals(Status.PAID, order.getStatus());
}

@Test
void should_throw_when_payFromCancelled() {
    Order order = new Order(Status.CANCELLED);
    assertThrows(IllegalStateException.class, order::pay);  // 终态拒绝
}

@Test
void should_throw_when_shipFromPendingPayment() {
    Order order = new Order(Status.PENDING_PAYMENT);
    assertThrows(IllegalStateException.class, order::ship);  // 跳跃转移拒绝
}
```

## 进阶：何时要测"迁移序列"（N-switch，N≥1）

0-覆盖只测单步迁移。当业务对**连续多步路径**有要求时，加测迁移序列（N-switch：连续 N+1 步）：

- **钱相关的**：必须测完整链路"待支付→已支付→已发货→已完成"，确认中途状态、金额、库存的一致性。
- **并发敏感的**：模拟"待支付"同时收到 pay 和 cancel，确认状态机是原子的（通常靠乐观锁/版本号，测试要覆盖冲突分支）。

多数业务 0-覆盖（单步）+ 全部非法迁移拦截 + 一条完整 happy 链路即足够。N-switch（多步序列）仅在上述高风险场景追加。

## 与枚举/状态模式的配合

如果状态机用**枚举**或**状态模式（State Pattern）**实现，非法迁移的拒绝逻辑通常集中在某处（`canTransitTo()` 或每个状态的 `handle()`）：

- 测试应直接针对**迁移判定方法**（`canTransitTo(from, to)`）做全矩阵测试——这是把"所有状态 × 所有状态"的组合一次测完，比逐个业务方法测更高效。
- 20 种组合（5 状态 × 4 操作）用 `@ParameterizedTest` 批量，区分"合法→通过""非法→拒绝"。

```
全矩阵（状态×操作）：
            pay   cancel  ship  confirm
待支付      ✓     ✓       ✗     ✗
已支付      ✗     ✗       ✓     ✗
已发货      ✗     ✗       ✗     ✓
已完成      ✗     ✗       ✗     ✗      ← 终态全拒绝
已取消      ✗     ✗       ✗     ✗      ← 终态全拒绝
```

这个矩阵就是测试设计的终极速查表——**每个 ✓ 和 ✗ 都是一个用例**。

## antipatterns

- **✗ 只测合法迁移（happy path 全绿）** → ✓ 必测所有非法迁移的拒绝，那是状态机测试的主战场。
- **✗ 不测终态**（"反正到终态就结束了"） → ✓ 从每个终态发起所有操作，确认全部拒绝（防复活/防回退）。
- **✗ 用"直接 setStatus()"绕过业务方法测** → ✓ 通过业务操作（`order.pay()`）触发迁移，测的是真实转移逻辑而非赋值。
- **✗ 忽略并发**（状态机有钱/库存时） → ✓ 至少测一个并发冲突分支（乐观锁版本号不一致 → 转移失败）。
- **✗ 状态图只存在脑子里** → ✓ 画出来（或列矩阵表），可视化是发现"漏掉的非法转移"的唯一可靠方式。
