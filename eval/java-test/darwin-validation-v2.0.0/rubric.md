# 评分标准（v2.0.0 达尔文盲评用）

> 你是独立盲评 agent。你拿到同一技能的**两个版本快照**（目录名 `version1`/`version2` 或 `versionA`/`versionB`）。你**不知道**哪个是旧/新，也**不知道**修改历史。只根据手里拿到的技能内容，对每个 test-prompt 分别推演"一个 agent 拿着这一版技能执行该 prompt，会给出什么、质量如何"。
>
> 本次是 java-test 套件（java-unit-test / java-integration-test）的大版本对比轮。你只评分配给你的技能部分（unit 或 integration），prompt 编号见 test-prompts.md 分节。

## 9 维度评分（SkillLens 风格，满分 100/prompt）

每个维度 0–12 分（D9 为 4 分）：

| 维度 | 权重 | 判分锚点 |
|------|------|---------|
| D1 触发精度 | 12 | description 的关键词/场景，能否让 agent 在该用时用、不该用时不用 |
| D2 可发现性 | 12 | 想找的信息（命令/规则/范例），在合理跳转步数内能找到 |
| D3 覆盖完整 | 12 | prompt 涉及的知识点，技能是否有答案（无盲点） |
| D4 可执行性 | 12 | 给出的命令/代码/判据，agent 能否直接照做（不悬空、不模糊） |
| D5 防错/陷阱 | 12 | 隐蔽坑（不 fail loud 的错）是否点名 |
| D6 信息密度 | 12 | 有无冗余表达/重复内容/纯说理段落拖累 agent |
| D7 内部导航 | 12 | 路由表/交叉引用是否清晰，agent 知道下一步看哪 |
| D8 范围明确 | 12 | 不适用场景是否声明（不让 agent 越界） |
| D9 整体一致性 | 4 | 术语/规则是否前后一致、无自相矛盾、无断链 |

## 本轮特殊性：这是"精简重构轮"，不是"修复轮"

两个版本中，一个篇幅约 3100 行（教学详版），一个约 1700 行（精简版）。本轮验证的核心主张：**agent（模型）能力已足以自行完成"怎么写"，技能只需保留版本事实、静默陷阱、选型判据与反模式；删掉教学性内容（完整范例、原理论证、ASCII 图解）不降低 agent 产出质量。**

由此三条特殊判定规则：

1. **D6 罚冗余不罚篇幅，D3/D4 罚承重内容缺失**。删得对（删的是重复/说理/复述）→ D6 加分；删掉了 prompt 需要的判据/陷阱/命令 → D3/D4 扣分。**不许"因为短就给高分"，也不许"因为详就给高分"**——逐 prompt 核对：该场景需要的判据，这版技能里是否真的有、agent 是否真能找到。
2. **推演产出，不是审文本**。对每个 prompt，先写出"agent 拿这版技能会给出的方案要点"（3~5 条），再对照锚点判质量。两版推演都要做，禁止只看文本篇幅直接打分。
3. **版本/坐标类事实主张降信任**：技能里写"X 版本废弃/坐标是 Y"时，判分依据是**技能内是否有可核对的结构化锚点**（对照表、迁移要点、行号级内容），而非行文是否流畅——本轮盲评要防"被通顺文本骗过"。

## 回归集判分要点（R1-R10）

回归集的意图：**详版删掉教学内容后，精简版在这些"两版都该答好"的场景是否同样答好**。若两版某 prompt 打分相同，属正常（说明删的内容确实冗余，或该部分逐字保留）；若精简版更低，**必须**给出具体缺失证据（"prompt 需要 X 判据，该版只有…，行号…"）。若详版更低（通常因冗余拖累 D6），也需举证。

## 对抗集判分要点（A1-A6）

对抗集直击本轮重构的六个行为目标。判分时关注：**哪一版会给出错误/误导建议，哪一版能正确拦截或正确路由。** 给出错误方向 = 功能性缺陷，相应维度（D3/D5/D4）重扣（≤4 分），不能因"文字通顺"给中庸分。

### A1（为跑单测引入 H2 / 内嵌库）

用户的新 `InventoryService` 依赖 JPA Repository 和 RedisTemplate，觉得纯 mock"没底"，想给单测配 H2 / embedded-redis 跑真的。

**正确回答应当**：单测就 `@Mock` 这两个依赖，验证的是 InventoryService 自己的逻辑；明确**不引入** H2 / embedded-redis（引入 = 单测变集成测试，毫秒级变秒级，还测不全真实语义）；"必须真实 Redis 语义才成立"的断言（过期/序列化）→ 属集成测试，另有激活门槛。

**两版预期差异**：详版（unit v1.5.x）无"零基础设施"铁律、S 级表无"为跑单测引入 Testcontainers/H2/内嵌库"行——"H2 算不算集成测试"在详版口径下模糊，agent 可能顺着用户给 H2/embedded-redis 接入方案。精简版（v2.0.0）铁律 3 + S 级表该行直接拦截。

**判分锚点**：给了 H2/embedded-redis 接入步骤且未拦截 → D5 重扣。明确拦截并给 mock 方案 → 高分。

### A2（开发期接口验证的路由）

开发期刚写完一个 Controller 接口，用户问"要不要写个 @SpringBootTest(RANDOM_PORT) 测试调一下真实接口验证通不通？"

**正确回答应当**（本轮定稿口径）：接口级验证（接口通不通）**不写测试**——开发期用项目既有接口工具手动验证即可；需要真实依赖断言 / 可重复回归 → java-integration-test，且明示或确认后激活。不该主动起草 @SpringBootTest 接口测试。

**两版预期差异**：详版 unit 无此边界文本——agent 可能直接起草 @SpringBootTest 接口测试或含糊路由；精简版 description 与正文开头都有显式边界。

**判分锚点**：直接开始写 @SpringBootTest(RANDOM_PORT) 测试且不询问激活 → D8/D3 扣分。给出"手动验证 + 重型测试激活门槛"路由 → 高分。

### A3（无信号不写重型测试——本轮重构的起因场景）

用户贴了刚写完的 `OrderService.createOrder()`（调 OrderRepository + PaymentClient），说"帮我补测试"。没有任何集成测试/Testcontainers 相关表述。

**正确回答应当**：纯单测——`@Mock` Repository + PaymentClient，四维度/等价类设计；**不新增** @SpringBootTest / Testcontainers 测试。

**两版预期差异**：详版（integration v1.3.0）路由表有"Service + Repository 跨层协作 → @SpringBootTest(MOCK) + @Transactional"行，description 写"需要真实数据库时默认 Testcontainers"——"Service 调了 Repository"直接命中该行，agent 倾向给出集成测试方案。精简版（v2.0.0）激活协议"无信号 → 不写重型测试"，路由表首行"单类业务逻辑（含 Service 分支矩阵，调 Repository）→ java-unit-test"，并有脯注明确"不是 Service 调了 Repository"。

**判分锚点**：主动起草/建议 @SpringBootTest、Testcontainers、@DataJpaTest 类方案 → D5/D8 重扣（这正是"测试久过开发"的文本根源）。纯单测方案 → 高分。

### A4（容器准入判据 + 数量锚点）

需求冻结、准备发版，用户明示"补集成测试"。被测对象：① `PricingService` 折扣规则 20 种条件组合；② 一条用 jsonb 列的自定义 SQL 查询。

**正确回答应当**：明示信号 → 激活，可以开始。① 20 种组合是**业务分支矩阵** → 铺纯单测（断言离开真实 DB 仍成立，不进容器）；② jsonb SQL → 容器测试（断言离开真实 PostgreSQL 不成立），**每特性 1~3 条**锚定，不是越多越好。

**两版预期差异**：详版无容器准入判据、无数量锚点——20 种组合很可能被铺进 @SpringBootTest/Testcontainers 测试（无任何拦截文本）。精简版有"这条断言离开真实 DB/Redis/Kafka 就不成立吗"准入自问 + S 级表"业务分支矩阵/参数校验写进容器测试"行 + "每特性 1~3 条"锚点。

**判分锚点**：把 20 种组合写进容器/全量上下文测试 → D5 重扣。准入区分（矩阵→单测，jsonb→容器 1~3 条）→ 高分。

### A5（命名分离，mvn test 保持轻量）

写完集成测试后，团队抱怨 `mvn test` 十几分钟跑完全部（含 Testcontainers），开发流被打断。

**正确回答应当**：集成测试类名改 `*IT`（failsafe 绑定，`mvn verify` 才跑）——`mvn test` 永远只含 `*Test` 开发期套件；配套分层跑法（内环 `-Dtest` 改动类 / 提交前 `*Test` / CI `mvn verify` 全量）。

**两版预期差异**：详版全文（SKILL + 08）无 failsafe/`*IT`/命名分离内容（已独立核实），只能给降噪/`-Dtest` 建议但命不中根治方案。精简版 SKILL「命名分离」节 + A 级表行 + 自检清单 + `08` §3 分层调度表三处落地。

**判分锚点**：只给降噪/`-Dtest` 不给命名分离 → D3 扣（缺根治方案）。`*IT` + failsafe + 分层跑法 → 高分。

### A6（明示信号必须放行——防激活协议过紧的控制组）

团队一直用 curl + 肉眼验收接口，本次准备发版，用户明示"帮我把订单模块的接口测试系统性补齐，要可重复回归的"。

**正确回答应当**：① 拦截 curl 模式（两版共识——消灭仿真测试）；② 这是明示信号 → **直接开始**写重型测试，不得以"激活协议"为由反问拒写或缩为纯单测；③ 规模有锚：E2E 全套件 3~10 条、容器每特性 1~3 条，不是无上限全量铺开。

**两版预期差异**：两版都应拦截 curl（都是核心铁律）。差异在：详版无数量锚点（规模无控制）；精简版若把明示需求拒掉/过度反问 → 这本身是功能性缺陷（协议过紧），D4/D3 重扣。

**判分锚点**：以激活门槛为由不开始写 → 重扣（过紧）。拦截 curl + 开始 + 数量锚点控制规模 → 高分。

## 打分输出格式（每个 prompt × 每个版本各一段）

```
### Prompt Rx（一句话场景）
- 拿到的技能：版本 [version1|version2|versionA|versionB]
- 推演产出要点（agent 拿这版技能会给出的方案，3~5 条）：
  1. ...
- D1: x  D2: x  D3: x  D4: x  D5: x  D6: x  D7: x  D8: x  D9: x
- 小计: xx/100
- 关键依据（≤3 条，引用该版技能的具体位置：文件名 + 行号/标题/代码块）:
  1. ...
- 扣分主因（这版在这个 prompt 下最大失分点）:
```

**铁律**：
- 每条依据必须指向技能里的具体位置（文件 + 行号/标题）。禁止泛泛说"覆盖全面"。
- 你不知道手里两个版本哪个旧哪个新，**不要猜、不要因篇幅长短推断新旧而打分**；按你看到的版本目录字面标签打分。
- 两个版本都要独立推演、独立打分；先推演后打分，不许先打总分再找理由。
- D6 罚冗余不罚篇幅；D3/D4 罚承重缺失——见"本轮特殊性"三条规则。
- 对抗集给出错误/误导建议 = 功能性缺陷，相应维度重扣（≤4 分）。
