# 评分标准（v1.5.0 回归验证盲评用）

> 你是独立盲评 agent。你拿到两份技能快照（version1 与 version2 / versionA 与 versionB，标签已打乱）。**只根据手里拿到的技能内容，对每个 test-prompt 分别在两份快照下给出判断。**
>
> 本次是 **v1.4.1 → v1.5.0** 的回归 + 对抗验证。共 11 条 prompt：R1-R7 回归集（确保五处改动没让原场景退步）、A1-A4 对抗集（直击本轮五处改动的根本原因）。

## 9 维度评分（SkillLens 风格，满分 100）

每个维度 0–12 分（D9 为 4 分），按"agent 拿着这套技能执行 prompt，能否产出合格结果"打分：

| 维度 | 权重 | 判分锚点 |
|------|------|---------|
| D1 触发精度 | 12 | description 里的关键词/场景/代码令牌，能否让 agent 在该用时用、不该用时不用 |
| D2 可发现性 | 12 | 想找的信息（命令/规则/范例），在合理跳转步数内能找到 |
| D3 覆盖完整 | 12 | prompt 涉及的知识点，技能是否有答案（无盲点） |
| D4 可执行性 | 12 | 给出的命令/代码/判据，agent 能否直接照做（不悬空、不模糊） |
| D5 防错/陷阱 | 12 | 隐蔽坑（不 fail loud 的错）是否点名 |
| D6 信息密度 | 12 | 有无冗余表达/重复内容/纯说理段落拖累 agent |
| D7 内部导航 | 12 | 路由表/交叉引用是否清晰，agent 知道下一步看哪 |
| D8 范围明确 | 12 | 不适用场景是否声明（不让 agent 越界） |
| D9 整体一致性 | 4 | 术语/规则是否前后一致、无自相矛盾 |

## 回归集（R1-R7）判分要点

这 7 条沿用既有验证场景。重点：**v1.5.0 五处改动（description 重写 / 06 重组为"§1 栈基线决策表 + §2 映射 + §3 Mock 坑 + §4 范围" / 覆盖率立场改写 / guide-pro 引用清零 / DoD 第二条改写）是否让这些原场景退步**。若某 prompt 在两版下打分相同，属正常（说明改动没碰该场景）；若某版更低，**必须**给出具体退步证据（行号）。

**特别盯三条**：
- **R3（DoD 引用）**：DoD 第二条从"分支覆盖无盲区 + 项目无 JaCoCo 时人工核对分支表或按成本收益决定是否接入"改为"分支盲区清零（Branch Missed = 0 判据）+ 有/无 JaCoCo 两路径"。判分时核实——新版是否仍完整回答"分支测到没怎么检查"，且判据更可执行；若新版让判定标准变得含糊 → D3/D4 扣分并给行号。
- **R4/R5（06 导航）**：06 结构大改——版本差异（Mockito 工件坑 / JUnit 4 差异表 / 依赖坐标）从三处散布收敛到 §1 决策表。判分时核实——新版从第 0 步探测到 §1 是否一步到位；若新版反而找不到某项版本知识（如 mockito-inline 工件坑、JUnit 4 参数化写法）→ D2/D7 扣分并给行号。
- **R6/R7（§3 Mock 坑）**：§3 内部重排（静态调用两节合并为"先重构注入 → 兜底 mockStatic"）。判分时核实——spy/doReturn、verify times、严格桩、wrapper any()/ArgumentCaptor、try-with-resources 这些坑是否全部仍在且可发现；丢了任何一个 → D5 扣分并给行号。

## 对抗集（A1-A4）判分要点

对抗集的目标是**验证本轮五处改动的根本原因是否被真正修掉**。判分时尤其关注：**旧口径是否会在这些场景下给出错误、误导或摇摆建议，而新口径能正确处理。**

### A1（覆盖率立场 + 无工具核对路径）

**正确回答应当**：
- (a) 团队既有 80% 门禁：**照做**（CI 策略层），但设计标准不降——四维度 + 分支盲区清零，不写无断言凑数测试；从零定策略才谈"关键模块设分支覆盖阈值、胶水豁免"。
- (b) 项目无 JaCoCo 且用户不想加插件：**读被测方法源码列 if/switch 分支清单，逐分支对照已设计用例核对**——默认路径不依赖工具。不应摇摆（既说"人工核对"又暗示"建议接入工具"）。

**两版预期差异**：
- **v1.4.1**：DoD 第二条写"项目无 JaCoCo 时：人工核对分支表，**或按'成本收益'决定是否接入**"——与 05/06 的"仅用户问及时才提接入"互相矛盾，agent 在 (b) 场景下行为摇摆（可能推用户装插件，违背用户"不想加插件"的诉求）；antipattern 修正案是"报告+趋势监控+关键模块设阈值+胶水豁免"四选项并列，无默认答案，(a) 场景回答发散。
- **v1.5.0**：立场一句话定死（要求分支盲区清零、不要求百分比），DoD 第二条给机械判据（Branch Missed = 0 / 人工清单全勾）+ 无 JaCoCo 时的明确路径（列分支清单核对，不推接入），antipattern 修正为两场景各一个默认答案。

**判分锚点**：(a) 若回答是四选项套餐且不给"照做+不降标准"的默认姿态 → D4 扣分。(b) 若回答摇摆或推接入工具（用户明说不愿加） → D4/D5 扣分。给出明确两路径 + 机械判据 → 高分。

### A2（非 Spring 项目引 AssertJ 坐标）

**正确回答应当**：给出 assertj-core 的 groupId/artifactId/scope=test 坐标（版本跟随项目/取最新稳定），且指向技能内可查到该坐标的位置。

**两版预期差异**：
- **v1.4.1**：SKILL.md 断言库策略节说"非 Spring 项目首次触发时按 references/06 §1 引入 assertj-core"，但 06 §1 的非 Spring 坐标块**从未列过 assertj-core**（只有 junit-jupiter / mockito-core）——指针悬空，agent 需自己拼坐标。
- **v1.5.0**：06 §1 非 Spring 坐标块的注释中含 assertj-core 完整坐标。

**判分锚点**：若该版本的 06 §1（或被指向的坐标处）实际可查到 assertj-core 坐标 → D4 高分；指针指向的位置没有该坐标（悬空） → D4/D2 扣分。

### A3（祖传大方法重构第一步 + "严重超标"判据）

**正确回答应当**：先特征测试锁现状（把当前实际输出录下来当期望值），再小步重构，最后补设计用例；并给出"认知复杂度 ≥~30 判为严重超标"之类的机械判据。

**两版预期差异**：
- **v1.4.1**：05 遗留代码节末尾把"严重超标方法"的定义指到 `java-coding-guide-pro/references/12-complexity.md`——**跨插件文件**，只装本技能（java-test 插件）的环境中该文件不存在，断链；本技能内无"多复杂算超标"的判据。
- **v1.5.0**：判据自包含（"认知复杂度 ≥~30 判为严重超标，先特征测试锁现状再拆解"），无外部依赖。

**判分锚点**：若该版本内可自包含回答（特征测试路线 + 阈值判据都在本技能文件内） → D4 高分；若必须引用一个本技能目录之外的文件才能给判据 → D4 扣分（可执行性悬空）。

### A4（description 触发令牌：贴代码求 review，不提框架名）

**正确回答应当**：这类"只贴测试代码、不提框架名"的 review 请求应能触发本技能；技能 description 中的触发信号应覆盖代码里出现的注解/方法令牌（@Mock / @InjectMocks / @ParameterizedTest / @MethodSource / when(...) / assertEquals 等）。

**两版预期差异**：
- **v1.4.1**：description 的触发信号以用户任务词/痛点为主（JUnit / Mockito / 测试用例 / 怎么测…），**无代码令牌通道**——纯贴代码场景匹配度弱。
- **v1.5.0**：description 新增"代码或 pom 中出现：spring-boot-starter-test、junit-jupiter、@Test / @BeforeEach / @ParameterizedTest / @MethodSource、assertEquals / assertThrows、@Mock / @InjectMocks / MockitoAnnotations.openMocks、mockStatic / MockedStatic、mockito-core"通道。

**判分锚点**：D1 直接按 description 令牌覆盖度打分——prompt 代码里的关键令牌（@InjectMocks / @ParameterizedTest / @MethodSource / when）在 description 中有无对应触发信号。同时 D6 注意：description 是否仍含大段价值论证/写给人看的营销话术（有 → D6 扣分）。

## 打分输出格式（每个 prompt × 每个版本必填）

```
### Prompt Rx/Ax（一句话场景描述）
- 拿到的技能：版本 [version1|version2]（A 组）或 [versionA|versionB]（B 组）
- D1: x  D2: x  D3: x  D4: x  D5: x  D6: x  D7: x  D8: x  D9: x
- 该 prompt 小计: xx/100
- 关键依据（≤3 条，引用具体行号或代码块）:
  1. ...
  2. ...
  3. ...
- 扣分主因（这个 prompt 在这个版本下最大的失分点）:
```

**铁律**：
- 每条依据必须能指向技能里的具体位置（行号 / 标题 / 代码块）。禁止泛泛说"覆盖全面"。
- D6（信息密度）：冗余越多扣分越重。读到"为什么这种方法好"的说理、重复别处的表格 → 扣分。
- D4（可执行性）：规则只说"要检查 X"但不说"怎么检查 X"（没有命令/列名/动作/坐标）→ 扣分。
- **对抗集（A1-A4）特别规则**：若某版本在该 prompt 下会给出**错误、误导或摇摆建议**（如无工具时推装插件 / 坐标指针悬空 / 判据依赖不存在的文件），这是**功能性缺陷**，相应维度（D4/D5/D2）应重扣（≤4 分），不能因"文字通顺"给中庸分。
- 不要因为版本号高低影响打分。版本号是元数据，与内容质量无关。
- 你不知道拿到的两个标签哪个对应旧/新版，按你看到的版本字面值打分即可，不要猜。
