# 评分标准（v1.4.0 达尔文盲评用）

> 你是独立盲评 agent。你**不知道**两个版本哪个是旧/新，也**不知道**技能的修改历史。**只根据手里拿到的技能内容，对每个 test-prompt 给出判断。**
>
> 本次是 **v1.3.2 → v1.4.0** 的回归 + 对抗验证。共 11 条 prompt：T1-T8 回归集（确保三处改动没让原场景退步）、T9-T11 对抗集（直击本次三条反馈的根本原因）。

## 9 维度评分（SkillLens 风格，满分 100）

每个维度 0–12 分（D9 为 4 分），按"agent 拿着这套技能执行 prompt，能否产出合格结果"打分：

| 维度 | 权重 | 判分锚点 |
|------|------|---------|
| D1 触发精度 | 12 | 描述里的关键词/场景，能否让 agent 在该用时用、不该用时不用 |
| D2 可发现性 | 12 | 想找的信息（命令/规则/范例），在合理跳转步数内能找到 |
| D3 覆盖完整 | 12 | prompt 涉及的知识点，技能是否有答案（无盲点） |
| D4 可执行性 | 12 | 给出的命令/代码/判据，agent 能否直接照做（不悬空、不模糊） |
| D5 防错/陷阱 | 12 | 隐蔽坑（不 fail loud 的错）是否点名 |
| D6 信息密度 | 12 | 有无冗余表达/重复内容/纯说理段落拖累 agent |
| D7 内部导航 | 12 | 路由表/交叉引用是否清晰，agent 知道下一步看哪 |
| D8 范围明确 | 12 | 不适用场景是否声明（不让 agent 越界） |
| D9 整体一致性 | 4 | 术语/规则是否前后一致、无自相矛盾 |

## 回归集（T1-T8）判分要点

这 8 条复用 v1.3.1 验证过的 prompt。重点：**v1.4.0 三处改动（AssertJ 范围 / @MockBean 装配 / DoD 锚点+05 精简）是否让这些原场景退步**。若某 prompt 在两版下打分相同，属正常（说明改动没碰该场景）；若 v1.4.0 更低，**必须**给出具体退步证据（行号）。

**特别盯 T6（停止信号可执行性）**：05 文件刚被精简（三信号展开 → 只留开放集陷阱），判定 checklist 移到了 SKILL.md DoD 锚点。判分时核实——
- 若 v1.4.0 让用户找不到判定标准（指针断了/内容删过头）→ D3/D7/D4 扣分，需给行号证据；
- 若 v1.4.0 通过 DoD 锚点仍能完整回答 T6（甚至更易引用）→ 不应仅因"内容换了位置"而扣分。

## 对抗集（T9-T11）判分要点

对抗集的目标是**验证三条反馈的根本原因是否被真正修掉**。判分时尤其关注：**v1.3.2（旧版）是否会在这些场景下给出错误或误导建议，而 v1.4.0（新版）能正确处理。**

### T9（反馈1 根因：表格型 VO 逐列断言）

用户在测一个 16 列 Excel 导出 VO 的 `toExportVO` 方法，同时还有一个 list 顺序校验子问题。

**正确回答应当**：
- (a) 16 列各列语义独立、各有字段名 → **用 JUnit 原生 `assertEquals` 逐列断言**（失败栈帧直接指到字段名，加列只改一处）。**不应**建议用 `extracting(16 fields).containsExactly(16 values)`——那会失败时报整个 tuple 不匹配、顺序敏感、难维护。
- (b) list 元素构成/顺序校验 → **应升级到 AssertJ** 的 `containsExactly` / `extracting(...)`。

**两版预期差异**：
- **v1.3.2**：断言库策略写"同一对象 3+ 字段断言 → extracting"——按字面执行，16 列 ≥ 3 会**误判为该用 extracting**，给出 (a) 错误建议（与"失败定位准"诉求矛盾）。(b) 部分两版都能答对（集合断言两版都覆盖）。
- **v1.4.0**：触发条件改为"集合内容断言 / 字段分组断言（同一逻辑组）"——16 列语义独立、非同一逻辑组 → **不触发升级，正确留在原生逐列断言**。(b) 部分仍正确升级。

**判分锚点**：(a) 若建议用 extracting 逐字段塞 16 个 → D3/D5 重扣（这是反馈1 的真实痛点）。正确留在原生 → 高分。(b) 升级到 AssertJ 集合断言 → 高分。

### T10（反馈2 根因：项目既定 mock 装配 vs @MockBean 滥用）

用户团队 spec 规定用 TestConfig + `@Bean` mock 的轻量容器装配，同事质疑违反规范；同时问真·`@MockBean` 起全量上下文是否有问题。

**正确回答应当**：
- (a) TestConfig 手写 `@Bean` mock 是**项目既定的合法装配模式**，不是反模式——应**跟随项目**，不应强推 `@Mock + @InjectMocks`。"违反单测规范"的质疑是误报。
- (b) 纯单测用 `@MockBean` + `@SpringBootTest` 起全量 Spring Context → **是真反模式**（会重建 Context，开销大），应改用切片测试或项目既定轻量装配。

**两版预期差异**：
- **v1.3.2**：S 级表 `@MockBean` 行只给一个正解"纯单测用 @Mock+@InjectMocks"，按字面执行 → (a) 会**误报** TestConfig 写法"应该改成 @InjectMocks"，给出错误迁移建议；(b) 能正确拦截。
- **v1.4.0**：S 级表补了"项目既定的 mock 装配模式（如 TestConfig 手写 @Bean mock 轻量容器）优先于本默认"且红线收窄到"@MockBean 起全量 Context" → (a) 正确跟随项目、不误报；(b) 仍正确拦截真反模式。

**判分锚点**：(a) 若建议把 TestConfig 迁移到 `@InjectMocks` → D3/D5 重扣（误报，违背栈中立铁律）。正确跟随项目 → 高分。(b) 两版都应正确，差异主要在 (a)。

### T11（反馈3 根因：DoD 写"覆盖率 ≥ 80%"）

团队 DoD 写"覆盖率 ≥ 80%"，用户质疑并希望改成可被 PR/checklist 引用的形式。

**正确回答应当**：
- 指出"覆盖率 ≥ 80% 当硬门禁"是反模式（把覆盖率当目标，催生凑数测试）；
- 给出**可被外部 checklist 引用的完成判定**：四维度齐全 + 分支覆盖无盲区 + 等价类清单已走完（三条同时满足）。

**两版预期差异**：
- **v1.3.2**：停止信号理论埋在 05，SKILL.md 无独立 DoD 锚点 → 能从 05 拼出正确答案，但**没有一个可被外部 checklist 直接引用的稳定锚点**，agent 需自己跨文件组装，可发现性/可引用性弱（D2/D7 扣分）。
- **v1.4.0**：SKILL.md 有独立「DoD 锚点」小节，3 个可勾选项 + 显式反例（✗ 覆盖率 ≥ 80% → ✓ 三条判定），且标注"可被外部 PR/DoD checklist 直接引用" → 直接命中，可发现性/可引用性强。

**判分锚点**：若只是泛泛说"覆盖率不是目标"但不给可引用的替代判定 → D4 扣分（不可执行）。给出可勾选 checklist → 高分。v1.4.0 的 DoD 锚点小节是直接证据。

## 打分输出格式（每个 prompt 必填）

```
### Prompt Tx（一句话场景描述）
- 拿到的技能：版本 [A|B]
- D1: x  D2: x  D3: x  D4: x  D5: x  D6: x  D7: x  D8: x  D9: x
- 该 prompt 小计: xx/100
- 关键依据（≤3 条，引用具体行号或代码块）:
  1. ...
  2. ...
  3. ...
- 扣分主因（这个 prompt 在这个版本下最大的失分点）:
```

**铁律**：
- 每条依据必须能指向技能里的具体位置（行号 / 标题 / 代码块）。禁止泛泛说"覆盖全面"。
- D6（信息密度）：冗余越多扣分越重。读到"为什么这种方法好"的说理、重复别处的表格、ASCII 图重复旁边表格 → 扣分。
- D4（可执行性）：规则只说"要检查 X"但不说"怎么检查 X"（没有命令/列名/动作）→ 扣分。
- **对抗集（T9/T10/T11）特别规则**：若某版本在该 prompt 下会给出**错误或误导建议**（如建议表格 VO 用 extracting / 建议把 TestConfig 迁到 @InjectMocks / 对 DoD 没给可引用判定），这是**功能性缺陷**，相应维度（D3/D5/D4）应重扣（≤4 分），不能因"文字通顺"给中庸分。
- 不要因为版本号高低影响打分。版本号是元数据，与内容质量无关。
- 你不知道 A/B 哪个是 v1.3.2 哪个是 v1.4.0，按你看到的版本字面值打分即可，不要猜。
