# java-contract D3 对照实验设计

> 目的：实测 `java-contract` 技能与契约文件在「需求没说明的边界决策」上的实际增益，
> 为「是否需要增加机制」提供数据，**不预设要加 hook**。
> 日期：2026-11-19 · 对象版本：java-contract 2.7.1 · 原则：隔离生成、客观判分、证据落盘。

## 一、三个实验组

| 组 | 条件 | 要回答的问题 |
|---|---|---|
| **A** | 无技能、无契约：只有任务书 | 现代 Java 模型裸写时的边界决策基线 |
| **B** | 带技能与契约：技能全文（`context/java-contract/`）+ 已播种的 `.claude/rules/java-contract.md`，提示先读两者 | 技能 + 契约文件全副武装时的上限 |
| **C** | 模拟 compact 后：上下文只剩任务书 + 一段压缩摘要（提到契约文件已落盘），契约文件仍在磁盘 | 上下文压缩丢失细节后，仅凭摘要唤起 + 契约文件还能保住多少 |

A/B/C 任务书完全相同（`task-prompt.md`），均只允许产出
`src/main/java/com/example/directory/MemberIndex.java` 与 `response.md`。
生成 agent 一律隔离：不得读取工作目录之外的任何文件（尤其不得读仓库的技能/eval），不联网。

## 二、任务与强制场景

`task-prompt.md`：实现 `MemberIndex` 四个方法（index / find / averageAge / groupByTeam），
数据来自外部导入。任务书刻意覆盖三个强制场景：

1. **无结果**——`find` 查不到、`averageAge` 对空集合；
2. **集合 null 元素**——列表里有 `null` 元素、`age` 字段无值；
3. **重复 key**——`index` 遇到重复 id。

## 三、记录项：契约八项命中 + 默认声明

**适用项**：①无结果 ②null 参数 ③集合 null 元素 ④重复 key ⑤返回集合形态 ⑦静态还是实例
（⑥非法参数 ⑧重复到达 本任务不可达，记 N/A）。

每项「命中」判据（依契约默认；本 fixture 无既有惯例，按默认判）：

| 项 | 命中 | 不命中 |
|---|---|---|
| ①无结果 | `find` 无 → `Optional`；`averageAge` 空 → `Optional`（或抛 `IllegalArgumentException` 要求先判空）；列表结果空集合 | `find`/聚合返回 `null`；空集合平均返回 `0` |
| ②null 参数 | 必填标量（id）`requireNonNull`/显式拒绝；**集合参数按空处理**（不用 `requireNonNull`）；不给必填编默认值 | 对集合参数抛 NPE；把 null id 静默当"全部"或空串 |
| ③集合 null 元素 | `null` 元素跳过，不整批失败；`age` 无值在平均里跳过整条记录 | 遇 `null` 元素抛 NPE/整批失败；`age` 当 0 计入平均 |
| ④重复 key | 重复 id `putIfAbsent` 保留首条（或 `put` 覆盖 + 注释说明原因） | 静默 last-wins 无注释；或直接抛异常且无声明理由 |
| ⑤返回集合形态 | 对外 Map/List 不可变（或防御拷贝）；Map 插入顺序可预期（`LinkedHashMap`）或明确声明不保序 | 可变内部结构直接外泄且无声明 |
| ⑦静态还是实例 | 四个纯函数方法 `static`、类内一致 | 纯函数做成实例方法 / static 与实例混用 |

**默认声明**（单独记录，不算进命中）：`response.md` 或 javadoc 是否逐场景写明决策规则；
是否声明依据（读到契约文件 / 技能默认 / 自行判断）；技能要求的「读不到契约时披露默认」是否出现。

**硬门槛**：`mvn -q compile` 通过；不过编译记 0 分并如实标注。

## 四、判分流程（防自评）

1. 生成 agent 各自落盘，互不可见。
2. 主 agent 先做编译门 + 逐项证据摘录（引用行号），不给印象分。
3. 盲评 agent 只看匿名快照（P/Q/R），按上表判命中，独立出一份判分。
4. 主 agent 对照盲评结果仲裁差异，证据写进 `report.md`。

## 五、机制决策规则（预注册，防事后找补）

设命中率 = 命中项 / 6（适用项）。

- **B ≥ 5/6 且 C ≤ 3/6**：压缩丢失显著 → 值得考虑唤起机制（hook 重注入 / 契约文件自动加载 /
  强化 javadoc 保险），再看 C 是否主动读了契约文件——读了仍弱 → 优先强化契约文件内容；
  没读 → 优先唤起机制。
- **B ≥ 5/6 且 C ≥ 5/6**：compact 影响小 → **不加机制**，维持技能 + 契约文件现状。
- **B ≤ 3/6**：技能武装后仍做不对 → 问题在技能内容，改正文，不加机制。
- 机制候选里 hook 只是其一；采用任何机制前先看 B/C 的失败模式落在哪一环。

## 六、实验后动作（任务既定，与数据无关）

复核两处内容矛盾：

1. 「库边界」推荐第三方库 ↔ description 与契约模板「不管第三方库选型」的范围声明冲突；
2. 「编译报错时」段的 JDK API 枚举（`List.of`/`isBlank`/`Stream.toList`）与开头
   「API 字典类内容不必再写」是否冗余。

**契约八项、六问定位法、审查七组原则上不动。**
