## 二、关键证据

**A 的唯一失分（②）正是技能瞄准的失分类**：`find(members, null)` 静默返回 `Optional.empty()`
（`runs/A/MemberIndex.java:75-77`），response.md 里明确取舍"任何输入都不抛异常（纯降级语义）"、
"null id 视作无主键的记录"——把「调用方传错」静默编成「查无此人」，恰是契约「不给必填参数编默认值」
要拦的决策。其余五项（Optional/putIfAbsent/跳过 null/不可变保序/static）裸写基线全部达标。

**C 完整恢复**：compact 摘要只保留一句"契约落盘在 .claude/rules/java-contract.md"，
C 主动读取该文件并逐条按默认实现（javadoc 与 response 均标注"契约依据"）。
其对④的解读还最贴默认原文："重复 key 保留首条仅约束以 id 为键的 index/find，
聚合不做去重——把保留首条外推为按 id 去重属于编造规则"（B 反而做了全方法去重的超纲扩展，
盲评备注两者均命中判据但 R 口径更窄）。

**B 的增益在交付纪律而非命中数**：逐条标注"契约第几节"、显式声明排除项（⑧对只读纯函数 N/A）、
按技能要求跑了契约分支冒烟（jshell 实测空入参/无结果/重复 key，给出具体输入输出）、
如实披露"无正式测试文件的原因是任务文件数约束"。C 的披露少一格：未交代"没跑什么"。

## 四、机制决策（按预注册规则）

B = 6/6 ≥ 5，C = 6/6 ≥ 5 → **「compact 影响小 → 不加机制」分支成立：不加 hook，
维持技能 + 契约文件现状。** 本实验不预设 hook，数据也不支持 hook：
契约文件在盘 + 摘要里一句路径提及即可让 post-compact 的 agent 完整恢复契约行为。

残余风险（如实记录）：

1. C 的恢复**依赖摘要保留了契约文件路径**。若压缩连这句也丢，预期退化到 A 的 5/6（②类静默默认重现）。
   暂不设机制，留观察：真实产品里压缩摘要一般保留关键文件引用。
2. 每组 N=1，任务未覆盖⑥/⑧；结论限定在「只读纯函数 + 边界三场景」范围内。
3. A 的基线 5/6 说明现代模型裸写时大方向不错；技能/契约的真实价值在**细粒度决策口径统一**
   （②fail-fast、字段无值按用途、范围声明）与**交付纪律**（依据可溯、验证与披露），不在救火式纠错。

## 五、实验后内容复核（任务既定动作）

1. **「库边界」↔「不管第三方库选型」冲突**：判定为表述边界不清而非实质冲突——
   「库边界」是编码中缺能力时的**一次性坐标补齐**（推荐一次、只给坐标、拒绝即用 JDK），
   与「第三方库 API 用法与选型咨询」不同。已改 description 与「库边界」节把这条边界写破。
2. **编译报错段 JDK API 枚举冗余**：开头既立"API 字典类内容不必再写"，
   （`List.of`/`isBlank`/`Stream.toList`）枚举违背该原则且非判据必需——已删枚举、
   保留判据句（"方法名属于 JDK 9+ 才引入的 API 时先怀疑版本"）。`var`/`record` 等语法信号保留。

八项、六问、审查七组未动。java-contract 2.7.1 → **2.8.0**（范围声明澄清 + 冗余删除）。
