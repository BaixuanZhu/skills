# 门禁协议全集（using-agile + 各业务技能共用）

本文件是三层门禁的权威来源。using-agile 在路由前守住「写前战略门禁」；各业务技能在产出时遵守「业务门禁 + 写完即停」。门禁管「何时必须停」，停下后如何提问/追问/审阅由 `probing-protocol.md`（探询协议）定义，两者同级配套。

## 一、写前战略门禁（最高优先级，覆盖所有写操作）

在**写入任何 `agile-docs/` 产物之前**（含第一份文件），必须先做「冲突 / 歧义预检」。一旦检测到以下任一情况，**立即停下、用表格列清单、请用户裁决，绝不在未确认时替用户假定战略基线或静默生成文件**：

- 多份输入文档战略方向矛盾（如一份主张 B2B、一份主张 C 端零售+分销）；
- 需求存在未界定的关键规则（MVP 边界、支付线上/线下、佣金比例、广告形态等）；
- 待写内容与现有 Vision / ADR 冲突；
- **该层必答话题清单存在未覆盖项**（缺失探测）——用户没提到 ≠ 不需要。此类触发的动作是**停下探询**（按 `probing-protocol.md §二/§三` 主动提问），而非停下裁决。

**预检清单**：
1. 输入是否来自多份可能矛盾的文档？→ 提取矛盾点。
2. 需求是否有未界定的关键规则？→ 列出待澄清项。
3. 将要写的内容是否与现有 Vision / ADR 冲突？→ 标出冲突。
4. 该层必答话题是否全部有明确答案或被用户明确跳过？→ 未覆盖项列入探询队列。

**若发现冲突/歧义 → 必须停下**：用表格呈现冲突点/待澄清项（每项附「建议」非「决定」），直接请用户裁决。在用户明确裁决前，不写任何产物文件（仅允许建目录骨架或写「待裁决」冲突记录 `STRATEGY_CONFLICT.md`）。

## 二、业务门禁（主动执行，不只是声明）

| # | 违反信号 | 拦截动作 | 合规路径 |
|---|----------|----------|----------|
| ① | 创建**技术任务**（T-NNN）却没有对应 **ADR** | 停下并说明：技术任务涉及架构决策时必须关联 ADR | 先补 ADR（在 ADR.md 中新增章节），再回填 T-NNN 关联字段 |
| ② | 要**直接修改**状态为「已接受」的 **ADR 章节** | 停下并说明：ADR 不可篡改 | 在 ADR.md 中新建章节标「替代 ADR-NNN」，原章节「状态」改"Superseded by ADR-XXX"，内容不动 |
| ③ | 有**未估算/未过 DoD/未验收**条目时要**关闭 Sprint** | 停下并列出未达标条目 | 逐条过 DoD → 未完成项退回 PRODUCT-BACKLOG 或延续下 Sprint → 再关闭 |
| ④ | 写 ADR 时**超出 4 行结构**或**包含禁止内容**（框架映射/候选方案对比/实现说明/安全细则/待办） | 停下并说明：ADR 是决策记录，不是设计文档 | 保留 4 行结构；细节移到代码仓库 docs/、DOD.md 或 PRODUCT-BACKLOG.md |

**门禁 ① 判定细则**：
- "涉及架构决策"的信号：引入新技术组件/中间件、改变数据流或容器边界、影响既有 ADR 决策——满足任一即需关联 ADR；在既有架构内实现的纯业务逻辑不算。
- **F-NNN（功能需求）默认不强制关联 ADR**（关联列可为 —）；功能明显依赖某条已有 ADR 时可选填。若某 F 条目实际命中上述信号，应改判为 T-NNN 并按本门禁处理。
- 现有 ADR 无合适章节可关联 → 回 agile-strategic 阶段 B 补 ADR 后再回填；**禁止发明"待 ADR-NNN 确认"之类的占位关联**（占位会让门禁 ① 失去校验意义）。

**禁止内容清单（写 ADR 即触发拦截）**：
- 框架映射表（如 yudao RBAC 映射）→ 代码仓库 `docs/`
- 候选方案对比表 → 代码仓库 `docs/research/` 或删除
- 详细实现说明 → 代码仓库 `docs/` 或代码注释
- 安全要求细则 → `DOD.md` 或代码仓库 `SECURITY.md`
- 待办事项 → `PRODUCT-BACKLOG.md`
- 长篇业务规则 → `VISION.md` 或代码业务文档

**执行原则**：拦截 ≠ 拒绝。始终以「要做 X，正确做法是先 Y」的建设性方式给合规路径。

## 三、边界与异常场景

| # | 异常场景 | 处理动作 |
|---|----------|----------|
| ① | 无 `agile-docs/` 却请求开 Sprint / 写故事 | 由 using-agile 建目录骨架，再继续 |
| ② | Backlog 为空（PRODUCT-BACKLOG.yaml 不存在或无条目）却要开 Sprint | 先引导创建至少 1 个条目，不创建空 Sprint |
| ③ | 请求多 Sprint 并行 | 本模型仅一个 current Sprint；确需并行建议拆两个项目实例 |
| ④ | Sprint 进行中大量加新需求 | 新需求先入 PRODUCT-BACKLOG 排序，下 Sprint 再纳入；仅 PO 正式中止重规划方可变更当前 Sprint |
| ⑤ | 架构反向验证失败但替代方案未定 | 调用 agile-strategic 在 ADR.md 建「待定」ADR 章节占位，方案定后补为正式 supersede |
| ⑥ | 条目过大无法估点（史诗级） | 拆为多个 T-/F- 条目再估斐波那契点 |
| ⑦ | DoD 未定义却要关闭/交付 Sprint | 先生成 DOD 逐条确认，再允许关闭 |

## 四、渐进式节奏（探询→产出→审阅循环）

- **探询（写前）**：按 `probing-protocol.md` 执行——以 PM/架构师姿态提问、追问、给候选，不自己假设后直接写。含糊答案、"你看着办"、必答话题缺失都有对应硬规则（`probing-protocol.md §二`）。
- **产出（单文档）**：探询确认后，只写当前这一个文档，不顺手写其他层。
- **暂停（写后）**：按 `probing-protocol.md §四` 做**结构化审阅**——先列「本文档中 agent 替用户做出的假设/决策」编号清单（区分用户给出/agent 推断/agent 推荐），请用户逐条确认，然后**停下等用户表态**。禁止只问「是否继续」。
- **推进（确认后）**：决策清单全部确认才进入下一个文档。

**三层间同样适用**：战略层全确认→才进 Backlog；Backlog 确认→才进 Sprint。

**业务技能硬约束**：每个业务技能只产本层文档，写完即停，询问「是否继续下一步」，不自动调用或暗示后续内容。下一阶段由用户主动触发对应技能（或再次调用 using-agile 做状态检测+路由）。

## 五、STRATEGY_CONFLICT.md 模板

写前战略门禁触发时，若需生成 `agile-docs/STRATEGY_CONFLICT.md`，模板见 `strategy-conflict-template.md`。该文件是临时占位，裁决后被业务技能吸收可删。
