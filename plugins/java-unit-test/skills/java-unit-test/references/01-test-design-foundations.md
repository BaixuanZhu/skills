# 01 · 测试设计思想基础

> 根文件，设计用例前必读。所有具体设计方法（02-04）建立在本文件的四维度模型上。

## 两条可执行原则

1. **补测场景先逆向还原**：等代码写完再补测试时，设计空间已被实现锁死——先逆向还原被测方法的输入空间与规则，再设计（而非照实现分支凑用例）。
2. **高风险域多投用例（Pareto）**：80% 的 bug 集中在 20% 的代码——复杂分支、高风险域（金额/日期/并发/加密）多分配用例，不平均用力。是否涉及钱/对外决定加码深度。

## 四维度模型：每个方法的必检清单

任何被测方法，**至少**回答这四组"有没有测到"——缺一个维度就是设计漏洞：

| 维度 | 测什么 | 设计方法 | 落地 |
|---|---|---|---|
| **正向** | 合法、正常输入的预期输出 | 有效等价类代表 | `assertEquals` |
| **反向** | 非法、异常输入的拒绝行为 | 无效等价类代表 | `assertThrows` |
| **边界** | 区间端点、空/null、极值 | 边界值分析 | `assertEquals` |
| **异常** | 业务异常/受检异常抛出路径 | 异常等价类 | `assertThrows` |

> 反向和异常维度是**新手最常漏**的。只写"传正常值返回正常结果"的测试，本质是 happy path 的复读机，测不出任何 bug。

### 一个具体例子：`divide(int a, int b)` 的四维度

```
被测：double divide(int a, int b)   返回 a/b

正向：divide(10, 2) == 5.0           有效等价类代表
反向：divide(10, 0)                  无效等价类 → 抛 ArithmeticException（或业务异常）
边界：divide(0, 5) == 0.0            分子为 0 的边界（0 是边界值）
      divide(Integer.MAX_VALUE, 1)   极大值边界（防溢出/精度）
异常：除数为 0 的异常路径已含在"反向"——此例反向=异常，正常
```

四维度不是"必须互斥的四类"，而是"四个视角的检视清单"。某些方法四维度会重叠（如上例反向=异常），关键是**四个视角都想过一遍**，而不是机械凑四个用例。

## 黑盒视角：只看输入输出，不看实现

设计测试用例时**优先用黑盒视角**（规格/接口契约），不要先钻进实现：

- ✗ 先读实现里有哪些 if 分支，再照着分支补用例 → 这是**白盒跟着代码走**，代码错了测试也跟着错（测试只是确认"代码做了它做的事"，而非"代码做了对的事"）。
- ✓ 先从接口签名、注释、业务规则推导**应有的输入输出契约**，设计用例，再用实现来校验覆盖率盲区。

> 白盒覆盖率的正确用法是**反向校验**（见 05）：设计完黑盒用例后，看哪些分支/行没被覆盖，那些是"设计漏了"或"死代码"的信号——而不是反过来"照分支写用例"。

## 好测试的硬约束（FIRST 里 S/A 表未覆盖的）

- **F**ast：毫秒级，不起外部容器（区别于集成测试的根本）。
- **R**epeatable：时间、随机数必须 mock 或注入固定值，跑 N 次结果一致。
- 其余（Isolated 不依赖顺序、Self-validating 有断言、一个测试一个行为）见 SKILL S/A 表。

## antipatterns

- **✗ "覆盖率到了 80% 就行"当唯一标准** → ✓ 覆盖率是反向诊断不是目标（见 05）。100% 行覆盖可能 0% 输入覆盖——只看数字仍易把它当合格证。
- **✗ 照着实现里的 if 分支补用例** → ✓ 黑盒先于白盒（见上文黑盒视角）：先从契约推导用例，再用覆盖率反向校验。照实现走=代码错测试跟着错。
