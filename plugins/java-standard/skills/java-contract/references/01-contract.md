# 01 · 契约六项

需求文档几乎不写这些，但它们决定调用方能不能安全地用你的方法。同一个方法，几种取舍都会静默生效、
都不报错，最后数据按不同规则落库。本文件给每项的判断依据与反例；默认值在 SKILL.md 的表里，
项目有不同做法时记进 `.claude/rules/java-contract.md` 的「本项目」列。

## 一、无结果返回什么

**识别判据：入参为空时，结果是「没有」还是「就是 0」。** 求和对空集合返回 0 是合法业务值（确实
一分钱没花），平均对空集合返回 0 是假数据（没有订单，客单价不存在）。同是聚合，前者返回 0，
后者返回 `Optional`——判断单位是「这个值有没有业务含义」，不是「方法叫什么」。

| 场景 | 返回 | 禁止 |
|---|---|---|
| 查询单条，可能不存在 | `Optional<T>` | 返回 `null` |
| 查询列表 | 空集合 `List.of()` / `Map.of()` | 返回 `null` |
| 聚合，0 是合法业务值（求和、计数） | `0` | — |
| 聚合，0 无业务含义（平均、最大、最小） | `Optional` | 返回 `0` |
| 布尔判断 | `false` | — |

`avgAmount` 对空集合返回 `0.00` 是典型误判：与「平均金额确实是 0」不可区分，报表上会多出一条假数据。
要么 `Optional` 让调用方决定，要么抛 `IllegalArgumentException` 要求调用方先判空。

「不返回 `null`」也管字段：DTO / VO 里的集合字段初始化成 `List.of()`，别留 `null` 等前端崩。

## 二、null 参数

**识别判据：`null` 有没有业务含义。** 按参数在方法里扮演的角色判断：

| 角色 | 例子 | 判断 |
|---|---|---|
| 参与定位 | `id`、`orderNo` | `null` 无法定位 → 必填 |
| 参与过滤 | `status`、`type` | `null` 常表示「不过滤」→ 可选，写进 javadoc |
| 作比较基准 | `threshold`、`minAmount` | `null` 没有比较对象 → 必填 |

| 参数性质 | 处理 |
|---|---|
| 必填（缺它无意义） | `Objects.requireNonNull(x, "x")`，fail fast |
| 可选（`null` 有业务含义） | 显式处理，javadoc 写清 `null` 表示什么 |
| 集合参数 | 按空集合处理，`null` 与空等价——**除非它本身是业务对象**，见第七节 |

**不给必填参数编默认值。** `hasAmountOver(orders, threshold)` 把 `threshold == null` 当作
`BigDecimal.ZERO` 后，方法等价于「是否存在金额大于 0 的订单」，几乎恒为 `true`。这类容错把
「调用方传错」变成「结果永远为真」，比抛 NPE 难查得多。

## 三、集合里的 null 元素

默认跳过，不参与计算，也不让整批失败。入参常来自外部（DB 查询、反序列化、第三方回调），
容忍脏元素比让调用方先清洗更符合业务预期。

若业务要求「有 null 就拒绝」，在方法开头显式校验并抛异常，写明校验意图——不要靠循环里的 `continue`
静默跳过再声称已校验。

## 四、重复 key

**识别判据：数据从外部来（DB 查询、文件导入、第三方回调）且 key 不唯一时，业务上要「先到的」
还是「最新的」。** 判不出就选保留首条——覆盖会让后到的脏数据悄悄替换正确值。

| 构造方式 | 重复时 | 何时用 |
|---|---|---|
| `putIfAbsent` | 保留首条 | **默认**：幂等导入、去重 |
| `put` | 后者覆盖 | 需要最新值（如按时间升序排过再覆盖），须注释说明 |
| `toMap` 两参 | 抛 `IllegalStateException` | 只有确定唯一时才用 |
| `toMap` 三参 `(a, b) -> a` | 保留首条 | 与 `putIfAbsent` 等价 |
| `toMap` 三参 `(a, b) -> b` | 保留末条 | 同上，需注释 |
| `groupingBy` | 天然聚合 | 同 key 需要合并而非择优时 |

`put` 与 `putIfAbsent` 的差别在重复数据上完全静默：同一份导入逻辑，写 `put` 的保留最后一条，
写 `putIfAbsent` 的保留第一条，两种都不报错，数据已经按不同规则落库。

## 五、非法参数

| 场景 | 默认 | 理由 |
|---|---|---|
| 分页 `pageNo < 1` | 纠正为 1 | 展示层容错，前端偶尔传 0 |
| 分页 `pageSize < 1` | 返回空列表 | 0 页无意义 |
| 分页越界 | 返回空列表，不抛异常 | 翻到末页之后是正常操作 |
| `topN` / `limit` 为负 | 返回空集合 | 同上 |
| 状态码 / 枚举值不认识 | 抛异常 | 领域层不猜 |

判据：**展示层容错，领域层 fail fast。** 分页、排序、每页条数是展示层；订单状态、支付渠道、业务类型
是领域层——后者遇到不认识的取值，静默映射成默认值等于把数据错误当正常处理。

## 六、静态还是实例

| 类型 | 选择 |
|---|---|
| 只依赖入参的纯函数 | `static` |
| 依赖注入的协作者（Repository、`Clock`、配置） | 实例方法 + 构造器注入 |
| 工具类 | `static` + `final` 类 + 私有构造器 |

同一个类内不混用：要么全 `static`，要么全实例。混用时调用方写法不同，合并代码那一步才会暴露。

## 七、两项冲突时听谁

六项在同一方法里会撞车。按这个顺序判：

| 冲突 | 听谁 |
|---|---|
| 集合参数：按空集合处理，还是 `requireNonNull`？ | 看它是**数据源**还是**业务对象**。数据源（`List<Order>` 供计算，空就是没有数据）→ 按空处理；业务对象（如「必须存在的订单列表」，空本身即错误）→ `requireNonNull` |
| 聚合无输入：返回 0 还是 `Optional`？ | 看 0 是否合法业务值（第一节判据）。求和 → 0；平均、最大、最小 → `Optional` |
| 单条查不到：`Optional` 还是 `null`？ | 项目惯例优先；无惯例用 `Optional` |
| 必填参数与「集合按空处理」同时适用 | 先判「它在方法里干什么」，再看类型。类型不是判据 |

**冲突时的处理顺序：项目契约文件的「本项目」列 → 本表 → 默认值。** 三者都没有，按默认落盘后
立刻写进契约——同一个项目里不同方法各自决定，是这类分歧最难查的形态。

## 八、怎么记录项目取值

默认值管不住的只有一种情况：**项目已有别的做法**。此时在契约文件的「本项目」列写实际做法，
不写理由（理由看这里），例如：

| 分歧点 | 默认 | 本项目 |
|---|---|---|
| 无结果 | 单条 `Optional` … | 单条返回 null，调用方按 `if (x == null)` 判；历史接口约定，不改 |

只记与默认不同的项。全取默认就整列留空——空列本身是信息，说明这个项目没有偏离。
