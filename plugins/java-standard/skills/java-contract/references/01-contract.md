# 01 · 契约七项

需求文档几乎不写这些，但它们决定调用方能不能安全地用你的方法。同一个方法，几种取舍都会静默生效、
都不报错，最后数据按不同规则落库。本文件给每项的判断依据与反例；默认值在 SKILL.md 的表里，
项目有不同做法时记进 `.claude/rules/java-contract.md` 的「本项目」列。

## 一、无结果返回什么

**识别判据：入参为空时，结果是「没有」还是「就是 0」。** 求和对空集合返回 0 是合法业务值（确实
一分钱没花），平均对空集合返回 0 是假数据（没有订单，客单价不存在）。同是聚合，前者返回 0，
后者返回 `Optional`——判断单位是「这个值有没有业务含义」，不是「方法叫什么」。

| 场景 | 返回 | 禁止 |
|---|---|---|
| 查询单条，可能不存在 | `Optional<T>` | 返回 `null` |
| 查询列表 | 空集合 `List.of()` / `Map.of()` | 返回 `null` |
| 聚合，0 是合法业务值（求和、计数） | `0` | — |
| 聚合，0 无业务含义（平均、最大、最小） | `Optional` | 返回 `0` |
| 布尔判断 | `false` | — |

`avgAmount` 对空集合返回 `0.00` 是典型误判：与「平均金额确实是 0」不可区分，报表上会多出一条假数据。
要么 `Optional` 让调用方决定，要么抛 `IllegalArgumentException` 要求调用方先判空。

「不返回 `null`」也管字段：DTO / VO 里的集合字段初始化成 `List.of()`，别留 `null` 等前端崩。

## 二、null 参数

**识别判据：`null` 有没有业务含义。** 按参数在方法里扮演的角色判断：

| 角色 | 例子 | 判断 |
|---|---|---|
| 参与定位 | `id`、`orderNo` | `null` 无法定位 → 必填 |
| 参与过滤 | `status`、`type` | `null` 常表示「不过滤」→ 可选，写进 javadoc |
| 作比较基准 | `threshold`、`minAmount` | `null` 没有比较对象 → 必填 |

| 参数性质 | 处理 |
|---|---|
| 必填（缺它无意义） | `Objects.requireNonNull(x, "x")`，fail fast |
| 可选（`null` 有业务含义） | 显式处理，javadoc 写清 `null` 表示什么 |
| 集合参数 | 按空集合处理，`null` 与空等价，**一律不用 `requireNonNull`**——业务要求非空时用 `isEmpty()` 校验，见第八节 |

**不给必填参数编默认值。** `hasAmountOver(orders, threshold)` 把 `threshold == null` 当作
`BigDecimal.ZERO` 后，方法等价于「是否存在金额大于 0 的订单」，几乎恒为 `true`。这类容错把
「调用方传错」变成「结果永远为真」，比抛 NPE 难查得多。

## 三、集合里的 null 元素

默认跳过，不参与计算，也不让整批失败。入参常来自外部（DB 查询、反序列化、第三方回调），
容忍脏元素比让调用方先清洗更符合业务预期。

**跳过要定在哪一层。** 三层各管一种情况，缺一层就会出现「同一份契约、两种结果」：

| 层 | 跳什么 | 说明 |
|---|---|---|
| 元素层 | 集合里的 `null` 元素 | 任何集合入参都先滤一遍 |
| 字段层 | 参与计算或拼接的**字段**为 `null` 或空白 | 「跳过」有两种读法——跳过这条记录，还是把这个字段当 0。按字段用途定，见下表 |
| 阶段层 | 过滤与分页的先后 | **先剔除、再切页**。分页有位置语义，先切再剔会让每页条数不固定 |

字段无值时怎么处理，取决于这个字段在方法里干什么：

| 字段用途 | 处理 | 理由 |
|---|---|---|
| 累加、平均、计数 | **跳过整条记录** | 用 0 代替会让合计偏低且不提示。金额缺失的订单按 0 计入后，会多出一个合计为 0 的分组，与「这个状态确实消费了 0 元」不可区分 |
| 拼接（`join`） | 跳过该值，其余照常拼接 | 结果里出现 `"a,,c"` 或 `"a, ,c"` 都是脏数据 |
| 排序、分页 | 保留记录，排在末尾 | 丢弃会改变条数，分页每页数量随之漂移 |

这三条都从同一条原则来：**0 与「无值」不是一回事**，任何把无值折成 0 的写法都会在报表上留下假数据。

`page([A1, null, A2, A3], 1, 2)` 返回 2 条（`[A1, A2]`）。先切页再剔 `null` 的写法返回 1 条，两种都不报错，
但前端翻页时每页条数忽多忽少，这种问题只能靠对数据才能发现。

若业务要求「有 null 就拒绝」，在方法开头显式校验并抛异常，写明校验意图——不要靠循环里的 `continue`
静默跳过再声称已校验。

## 四、重复 key

**识别判据：数据从外部来（DB 查询、文件导入、第三方回调）且 key 不唯一时，业务上要「先到的」
还是「最新的」。** 判不出就选保留首条——覆盖会让后到的脏数据悄悄替换正确值。

| 构造方式 | 重复时 | 何时用 |
|---|---|---|
| `putIfAbsent` | 保留首条 | **默认**：幂等导入、去重 |
| `put` | 后者覆盖 | 需要最新值（如按时间升序排过再覆盖），须注释说明 |
| `toMap` 两参 | 抛 `IllegalStateException` | 只有确定唯一时才用 |
| `toMap` 三参 `(a, b) -> a` | 保留首条 | 与 `putIfAbsent` 等价 |
| `toMap` 三参 `(a, b) -> b` | 保留末条 | 同上，需注释 |
| `groupingBy` | 天然聚合 | 同 key 需要合并而非择优时 |

`put` 与 `putIfAbsent` 的差别在重复数据上完全静默：同一份导入逻辑，写 `put` 的保留最后一条，
写 `putIfAbsent` 的保留第一条，两种都不报错，数据已经按不同规则落库。

## 五、非法参数

| 场景 | 默认 | 理由 |
|---|---|---|
| 分页 `pageNo < 1` | 纠正为 1 | 展示层容错，前端偶尔传 0 |
| 分页 `pageSize < 1` | 返回空列表 | 0 页无意义 |
| 分页越界 | 返回空列表，不抛异常 | 翻到末页之后是正常操作 |
| `topN` / `limit` 为负 | 返回空集合 | 同上 |
| 状态码 / 枚举值不认识 | 抛异常 | 领域层不猜 |

判据：**展示层容错，领域层 fail fast。** 分页、排序、每页条数是展示层；订单状态、支付渠道、业务类型
是领域层——后者遇到不认识的取值，静默映射成默认值等于把数据错误当正常处理。

**抛哪种异常**：参数本身违规（负数、空串、长度越界）→ `IllegalArgumentException`；业务规则不满足
（这个状态不允许该操作）→ 项目**已有**的业务异常类型，没有就用 `IllegalStateException`。不为这件事
新造异常类：调用方捕获的是既有的那几个，新类型等于没人处理，最终落到全局兜底变成 500。

## 六、静态还是实例

| 类型 | 选择 |
|---|---|
| 只依赖入参的纯函数 | `static` |
| 依赖注入的协作者（Repository、`Clock`、配置） | 实例方法 + 构造器注入 |
| 工具类 | `static` + `final` 类 + 私有构造器 |

同一个类内不混用：要么全 `static`，要么全实例。混用时调用方写法不同，合并代码那一步才会暴露。

## 七、返回集合的顺序与可变性

按 key 汇总返回 `Map` 时，默认保插入顺序，遍历结果可预期：

| 构造方式 | 遍历顺序 |
|---|---|
| `Collectors.groupingBy(...)` | `HashMap`，**没有约定**。key 的排列随 hash 而定，换 JDK 版本可能变 |
| `groupingBy(..., LinkedHashMap::new, ...)` | 首次出现顺序 —— **默认** |
| `Collectors.toMap(...)` 两参 / 三参 | `HashMap`，无序；要顺序传 `LinkedHashMap::new` 作第四参 |
| `TreeMap` | key 字典序 |

同一个 `sumByStatus`，返回 `TreeMap` 的遍历出 `[PAID, UNPAID]`，返回 `LinkedHashMap` 的出 `[UNPAID, PAID]`，
数值完全相同，报表分组顺序不同。要字典序就显式 `TreeMap` 并注释一句，不要留在 `HashMap` 的无序状态。

**方法返回值是对外契约，调用方无从判断顺序哪天会变。** 纯内部查找用 `HashMap` 没有影响，对外返回就定下来；
需要字典序（状态、类型、枚举名）用 `TreeMap`，否则用 `LinkedHashMap`。

**可变性同理，默认不可变**：

| 目标 JDK | 做法 |
|---|---|
| 9+ | `List.copyOf(x)` / `Set.copyOf(x)`；**要保序的 `Map` 不能用 `Map.copyOf`**——它不保证迭代顺序，用 `Collections.unmodifiableMap(new LinkedHashMap<>(x))` |
| 8 | `Collections.unmodifiableList(new ArrayList<>(x))`，不要只包一层 `unmodifiableList(x)`——那是视图，原集合变了照样跟着变 |

返回可变副本等于承诺「调用方可以改，且不影响我」，之后一旦优化成返回内部集合就静默破坏这个承诺。
要改的调用方自己 `new ArrayList<>(result)`，一行且意图清楚，比事后排查「谁改了返回值」便宜。
方法内部用完即弃的集合不用包。

## 八、两项冲突时听谁

七项在同一方法里会撞车。按这个顺序判：

| 冲突 | 听谁 |
|---|---|
| 集合参数：按空集合处理，还是 `requireNonNull`？ | **默认按空处理**。`null` 与空在这种方法里几乎没有语义差别，区分它们只是给调用方制造两种失败。例外只有一种：元素存在本身是业务前提（如「审批必须至少一个节点」），此时用 `isEmpty()` 校验并抛业务异常——仍然不用 `requireNonNull`，要卡的是「没有元素」，不是「传了 null」 |
| 聚合无输入：返回 0 还是 `Optional`？ | 看 0 是否合法业务值（第一节判据）。求和 → 0；平均、最大、最小 → `Optional` |
| 单条查不到：`Optional` 还是 `null`？ | 项目惯例优先；无惯例用 `Optional` |
| 「必填参数 `requireNonNull`」与「集合按空处理」同时适用 | 集合参数一律走后者。真正的必填是其中的**标量**参数（`threshold`、`id`），不是集合本身 |
| 聚合结果要顺序吗？ | 方法对外返回 `Map` 或 `List` 时定顺序与可变性（第七节）；只在方法内部用完即弃的 `HashMap` 不管 |

**冲突时的处理顺序：项目契约文件的「本项目」列 → 本表 → 默认值。** 三者都没有，按默认落盘后
立刻写进契约——同一个项目里不同方法各自决定，是这类分歧最难查的形态。

## 九、怎么记录项目取值

默认值管不住的只有一种情况：**项目已有别的做法**。此时在契约文件的「本项目」列写实际做法，
不写理由（理由看这里），例如：

| 分歧点 | 默认 | 本项目 |
|---|---|---|
| 无结果 | 单条 `Optional` … | 单条返回 null，调用方按 `if (x == null)` 判；历史接口约定，不改 |

只记与默认不同的项。全取默认就整列留空——空列本身是信息，说明这个项目没有偏离。
