# 03 · 决策表（多条件组合）

> 适用：结果由**多个条件组合**决定的逻辑（促销规则、费率档位、权限矩阵、计费阶梯）。决策表把"条件组合 → 动作"的关系**穷尽列出**，每一列就是一个用例——**列数 = 用例数**，不漏不重。

## 什么时候用决策表（而非等价类）

等价类处理的是**单个输入**的取值空间；决策表处理的是**多个输入条件的组合**。判别信号：

- 被测逻辑里有 2+ 个 `if/switch` 条件，且结果取决于它们的**组合**而非各自独立 → 决策表。
- 业务规则描述里出现"当 A 且 B 时…；当 A 且非 B 时…；当非 A 且 B 时…"这类组合语言 → 决策表。
- 条件组合数 ≥ 4（2 个条件各 2 值 = 4 组合） → 人脑易漏，必须列表。

> 一个反例：`discount = price * rate`，price 和 rate 各自独立影响结果，不组合 → 用等价类（02），不用决策表。

## 决策表结构（四栏）

| 条件桩 | 条件条目（每列一种组合） |
|---|---|
| 动作桩 | 动作条目（每列对应的动作） |

每一**列** = 一种条件组合 = 一个测试用例。完整示例见下文。

## 完整示例：促销折扣决策表

**业务规则**：订单折扣由"是否会员 + 是否满 100 元 + 是否有优惠券"组合决定：
- 会员 + 满 100 + 有券 → 7 折
- 会员 + 满 100 + 无券 → 8 折
- 会员 + 不满 100 → 9 折（有无券都一样，券不叠加）
- 非会员 + 满 100 + 有券 → 8.5 折
- 非会员 + 满 100 + 无券 → 不打折
- 非会员 + 不满 100 → 不打折

### 步骤 1：列出原始决策表（穷尽组合）

3 个条件，各 2 值 → 全组合 8 列：

| 条件/动作 | C1 | C2 | C3 | C4 | C5 | C6 | C7 | C8 |
|---|---|---|---|---|---|---|---|---|
| 会员？ | Y | Y | Y | Y | N | N | N | N |
| 满100？ | Y | Y | N | N | Y | Y | N | N |
| 有券？ | Y | N | Y | N | Y | N | Y | N |
| **折扣** | 7折 | 8折 | 9折 | 9折 | 8.5折 | 无 | 无 | 无 |

### 步骤 2：合并相同动作的列（化简）

观察：C3 和 C4 动作相同（都是 9 折，"不满100时券无效"）；C6/C7/C8 动作相同（非会员且不满100 或 无券 = 无折扣）。

化简后决策表（合并等价列）：

| 条件/动作 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 会员？ | Y | Y | Y | N | N |
| 满100？ | Y | Y | N | Y | — |
| 有券？ | Y | N | — | Y | N |
| **折扣** | 7折 | 8折 | 9折 | 8.5折 | 无 |

> "—" 表示该条件**不影响**此列结果（无关项）。化简后 **5 列 = 5 个用例**，覆盖所有业务分支。

### 步骤 3：5 列 → 5 个用例

| 用例 | 会员 | 满百 | 有券 | 期望折扣 | 覆盖业务规则 |
|---|---|---|---|---|---|
| 1 | 是 | 是 | 是 | 7折 | 会员满额叠加券 |
| 2 | 是 | 是 | 否 | 8折 | 会员满额无券 |
| 3 | 是 | 否 | （任意） | 9折 | 会员不满额（券无效，合并） |
| 4 | 否 | 是 | 是 | 8.5折 | 非会员满额有券 |
| 5 | 否 | — | 否 | 无 | 非会员无券（合并） |

> **注意用例 3**：测试时"有券"取一个值即可（合并后该条件无关），但实战中可顺手补一个"会员+不满百+有券"确认券确实被忽略——这是验证"无关项"的额外保险。

### 步骤 4：落地

每个用例一个 `@Test`，或用 `@ParameterizedTest` + `@CsvSource` 把决策表当数据源（每列对应一行 CsvSource 数据）。多条件组合**不宜**塞进单个 `@Test`——每列是独立业务规则。写法见 `references/06` §2。

## 化简规则

1. **相同动作 + 无关条件 → 合并**：两列动作相同，且某条件在一列 Y 一列 N → 该条件无关，合并为一列，条件标"—"。
2. **不可合并**：动作不同的列必须保留为独立用例。
3. **不要过度化简**：化简到 5 列是合理的，强行压到 3 列可能丢失对"无关项"的验证价值。

## 何时该引入决策表的工程信号

- 同一个方法里 `if` 嵌套超过 2 层且判断不同条件 → 决策表（也可能是"该重构为策略 Map/规则引擎"的信号）。
- Bug 反复出现在"某种条件组合" → 当前测试漏了该组合，补决策表。

## antipatterns

- **✗ 列出组合但忘了化简，8 个用例里 3 对冗余** → ✓ 合并相同动作的列（标无关项"—"）。
- **✗ 只列"全 Y"和"全 N"两列**（最满意/最不满意组合） → ✓ 穷尽所有组合，中间态组合才是 bug 高发区。
- **✗ 条件条目写了不可能的组合**（如"满100=N 且 amount=150"自相矛盾） → ✓ 每列必须是合法可构造的输入。
- **✗ 把决策表测试和等价类测试割裂**（重做一遍） → ✓ 决策表的每列本身就是一组等价类组合，是等价类在多条件场景的特化。
