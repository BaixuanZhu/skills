# 02 · 设计方法速查：等价类+边界值 / 决策表 / 状态迁移

> 三种方法的判据、计数规则与最典型漏测形态。落代码映射见 `04` §2。

## 等价类划分 + 边界值（最高频，覆盖 ~80% 纯输入→输出场景）

**判据**：结果由单个输入（或各自独立的多个输入）的取值决定。

- **有效等价类**：符合契约的输入 → 对应"正向"。**无效等价类**：违反契约的输入 → 对应"反向/异常"。**无效类往往比有效类多**（`[1,100]` 有 1 个有效类，却有 `<1`/`>100`/`null`/非数字等多个无效类）。
- **划分规则**：按"会走不同处理分支"切（行为差异，非数值大小）——✗ `[1,100]` 切成 `[1,50]`/`[51,100]`（行为可能一样，白费）✓ 一个有效类 + `<1`/`>100` 两个无效类。
- **计数**：**3~8 个有效/边界用例 + 每个无效等价类 1 个反向用例**，通常共 5~10 个。一类一代表，省下的额度测边界和无效类。
- **两个输入的无效类单独测**（一次只让一个输入非法，定位清晰）；有效类才组合。

**边界值表**（闭区间必测 `min-1, min, max, max+1`）：

| 输入类型 | 边界值 |
|---|---|
| 数值区间 `[min,max]` | `min-1, min, max, max+1` |
| 有序集合/列表（长度 n） | `0`（空）、`1`（单元素）、`n`（满）、`n+1`（越界） |
| 字符串 | `""`、`null`、`1` 字符、`maxLength`、`maxLength+1`、纯空白 |
| 日期 | 区间两端 + 跨天/跨月/跨年/闰年 2-29 + 时区切换点 |
| 索引/分页 | `0`、`1`、`size-1`、`size`（越界）、负数；`page=0`/`page=1`（0 基 1 基常混） |

**高风险域边界优先**（off-by-one 与精度重灾区）：金额（`0`、负数、`0.005` 四舍五入、溢出、小数位超 scale）、日期时间（`00:00:00`/`23:59:59`、月末、闰年、`now()` 的 mock）、集合容量（空、恰好容量、扩容点）。

**antipatterns**：
- ✗ 只测有效等价类 → ✓ 补全每个无效类，反向用例是发现 bug 的主力。
- ✗ 同类取多个代表（测 `1,2,3,4,5` 都在 `[1,100]` 内）→ ✓ 一类一代表。
- ✗ `null` 从不测（"调用方不会传"）→ ✓ `null` 是独立无效等价类，`@Nullable` 参数必测。
- ✗ 两个非法输入同时传入 → ✓ 一次一个非法输入。
- ✗ 浮点用 `==` 断言 → ✓ `assertEquals(expected, actual, delta)` 或改整数单位（如"分"）。

## 决策表（多条件组合）

**判据**：结果取决于 2+ 个条件的**组合**（促销规则、费率档位、权限矩阵、计费阶梯）。信号：业务规则里出现"当 A 且 B 时…；当 A 且非 B 时…"；条件组合数 ≥ 4。

反例：`discount = price * rate`，两输入各自独立影响结果，不组合 → 用等价类，不用决策表。

**结构**：条件桩 × 动作桩，每**列** = 一种条件组合 = 一个用例——**列数 = 用例数**，不漏不重。

**化简规则**：
1. 两列动作相同且某条件一列 Y 一列 N → 该条件无关，合并为一列，条件标"—"。
2. 动作不同的列必须保留为独立用例。
3. 不过度化简——强行压缩会丢失对"无关项"的验证价值（实战中可顺手补一列确认无关条件确实被忽略）。

**落地**：每列一个 `@Test`，或 `@ParameterizedTest` + `@CsvSource`（每列一行）。多条件组合**不宜**塞进单个 `@Test`。

**工程信号**：同一方法 `if` 嵌套超 2 层判断不同条件 → 决策表（也可能是该重构为策略 Map/规则引擎的信号）；bug 反复出现在"某种条件组合" → 补决策表。

**antipatterns**：
- ✗ 列出组合但忘了化简，8 用例里 3 对冗余 → ✓ 合并相同动作的列。
- ✗ 只列"全 Y"和"全 N"两列 → ✓ 穷尽组合，中间态组合才是 bug 高发区。
- ✗ 条件条目写了不可能的组合（自相矛盾的输入）→ ✓ 每列必须合法可构造。

## 状态迁移（有状态对象）

**判据**：被测对象有状态字段（status/state/phase），方法执行结果取决于当前状态（订单/审批/支付/工单状态机）。bug 几乎都不在正常流转，而在：非法转移未被拒绝、并发转移冲突、终态泄漏。

**必测三件**：

1. **合法迁移（0-覆盖）**：每条边一个用例（`待支付 --pay()--> 已支付`），断言终态 + 迁移动作（记录支付时间/释放库存）。
2. **非法迁移**：每个非法转移的拒绝——防重复支付（已支付再 `pay()`）、防僵尸复活（已取消再 `pay()`）、防跳跃（待支付直接 `ship()`）、防终态回退。
3. **终态验证**：从每个终态发起所有操作，确认全部拒绝。

**全矩阵速查**（状态 × 操作，每个 ✓ 和 ✗ 都是一个用例）：

```
            pay   cancel  ship  confirm
待支付      ✓     ✓       ✗     ✗
已支付      ✗     ✗       ✓     ✗
已发货      ✗     ✗       ✗     ✓
已完成      ✗     ✗       ✗     ✗      ← 终态全拒绝
已取消      ✗     ✗       ✗     ✗      ← 终态全拒绝
```

- 状态机用枚举/状态模式实现且拒绝逻辑集中在 `canTransitTo()` 时，直接对该判定方法做全矩阵 `@ParameterizedTest`，比逐个业务方法测更高效。
- **何时加测迁移序列（N-switch）**：钱相关（完整链路一致性）、并发敏感（pay 和 cancel 同时到，乐观锁冲突分支）。多数业务 0-覆盖 + 全部非法拦截 + 一条完整 happy 链路即够。

**antipatterns**：
- ✗ 只测合法迁移（happy path 全绿）→ ✓ 非法迁移的拒绝才是状态机测试的主战场。
- ✗ 不测终态 → ✓ 从每个终态发起所有操作，防复活/防回退。
- ✗ 用"直接 setStatus()"绕过业务方法 → ✓ 通过业务操作触发迁移，测真实转移逻辑。
- ✗ 状态机有钱/库存时忽略并发 → ✓ 至少测一个乐观锁冲突分支。
- ✗ 状态图只存在脑子里 → ✓ 列矩阵表，可视化是发现"漏掉的非法转移"的唯一可靠方式。
