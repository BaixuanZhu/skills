# 05 · 写多少：覆盖率反向校验 + 成本收益

> 回答开发者最常问的问题："**测试要写到什么程度才算够？**" 答案不是"覆盖率到 X%"，而是把覆盖率当作**反向诊断工具**，再叠加成本收益判断。

## 核心立场：覆盖率是必要的，但远远不够

### 覆盖率能做什么 / 不能做什么

| | 说明 |
|---|---|
| ✗ **覆盖率不是充分条件** | 100% 行覆盖可能 0% 输入覆盖——一行 `if (x > 0)` 被一个 `x=5` 跑过即"覆盖"，但 `x=0`、`x=-1`、`x=Integer.MAX_VALUE` 这些等价类都没测。 |
| ✗ **覆盖率不是目标** | 追"80% 覆盖率"会催生无脑凑数测试（测 getter/setter），数字好看但无价值。 |
| ✓ **覆盖率是反向诊断** | 设计完黑盒用例后，看哪些分支/行**没被覆盖**——那些是"设计漏了"或"死代码"的信号。 |

> 一句话：**覆盖率不告诉你"测够了"，只告诉你"明显还没测到哪"。** 它是探照灯，不是合格证。

## 四种覆盖率粒度（由弱到强）

| 粒度 | 含义 | 说明 |
|---|---|---|
| **行覆盖** | 每条可执行语句被执行过 | 最弱。`if(x>0)` 跑一次即覆盖，不管 x 正负。 |
| **分支覆盖**（C1） | 每个分支的 true/false 都走过 | 比 行覆盖 强：`if` 的两边都要测。 |
| **路径覆盖** | 所有执行路径组合 | 最强但通常不可达（组合爆炸），实战不追求。 |
| **MC/DC** | 条件组合中每个子条件独立影响结果 | 航空/安全级才用，普通业务测试不必。 |

**实战基准：以分支覆盖（C1）为校验口径**，行覆盖作辅助。JaCoCo 默认报告同时给两者。不要追求路径覆盖。

## 反向校验流程（覆盖率如何指导设计）

```
1. 先用黑盒方法设计用例（等价类/边界值/决策表/状态）   ← 正向设计
2. 跑测试，看覆盖率报告
3. 找未覆盖的分支/行：
   ├─ 是"应测但漏了"的分支 → 补对应等价类/边界用例      ← 覆盖率补盲区
   └─ 是"不可能进入"的死代码  → 标记，提示用户清理
4. 不要反过来：照着分支表逐个补用例凑覆盖率            ← 白盒驱动，本末倒置
```

### 关键：覆盖率是"设计完整性"的体检，不是设计本身

✗ 错误流程：打开覆盖率报告 → 发现 `line 42` 没覆盖 → 随便写个用例让它执行 → 覆盖率 +1%。这是**用覆盖率驱动设计**，结果是一堆"执行了但没断言关键行为"的废测试。
✓ 正确流程：黑盒设计 → 覆盖率报告暴露盲区 → 思考"这个分支对应哪个等价类/边界" → **补一个有断言的设计用例**。

## JaCoCo 接入（仅项目未有时，触发 C-CHECK）

Spring Boot 项目 `spring-boot-starter-parent` 内置 JaCoCo profile，加插件即可：

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.12</version>
    <executions>
        <execution>
            <goals><goal>prepare-agent</goal></goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>test</phase>
            <goals><goal>report</goal></goals>
        </execution>
    </executions>
</plugin>
```

`mvn test` 后看 `target/site/jacoco/index.html`。**仅当用户问"覆盖率/测够没/接入 jacoco"且项目无时才提**——普通设计用例不必主动推接入。

## "写多少"的成本收益判断

不要把所有方法一视同仁。用 **变更频率 × 业务风险** 决定投入：

```
                    业务风险
              低 ─────────────── 高
         高 │  适度测试          │  重点测试（结算/订单/支付/权限）
变更频率     │  （核心路径+边界） │  （全等价类+全边界+决策表）
         低 │  轻量测试          │  关键测试（金额/异常路径）
             │  （happy+1边界）  │  其余靠类型与编译保障
```

### 该重点测（多投用例）

- **涉及钱的**：金额计算、折扣、结算（off-by-one 即资损）。
- **对外契约**：API 入参校验、对外开放接口。
- **高频变更**：最近 3 个月改动多的方法（回归价值高）。
- **复杂分支**：嵌套 if/switch 多条件 → 用决策表覆盖所有组合。

### 可轻量测（少投用例）

- 纯 POJO 的 getter/setter（不值得测，Lombok 生成更可靠）。
- 框架胶水代码（`@RestController` 转发到 Service，逻辑在框架里）。
- 极少变更且低风险的工具方法（happy path + 一个边界足矣）。

> 这不是"偷懒"，是 **Pareto 原则**的应用（见 01）：80% 的 bug 在 20% 的代码，把用例预算投到那 20%。

## 什么时候算"够了"——三个停止信号

设计用例时，满足以下任一即可停止加用例（不是穷尽，是最小充分）：

1. **四维度齐全**：正向、反向、边界、异常都至少有一个代表（见 01）。
2. **分支覆盖（C1）无盲区**：所有 `if/switch` 的每个分支都被至少一个用例走到。
3. **等价类无遗漏**：列出的有效/无效等价类都有代表用例（02 的清单划完）。

三者**同时**满足 = 最小充分集。再多加的就是"同质冗余"（同一等价类的变体），价值递减。

## 过度测试也是一种缺陷

- **✗ 每个 getter/setter 一个测试** → ✓ POJO 用 Lombok，不测；或一个 `@ParameterizedTest` 批量。
- **✗ 同一分支测 5 个不同正常值** → ✓ 一个代表值足矣，省额度测边界。
- **✗ 测私有方法**（反射破坏封装） → ✓ 通过公有方法间接测；私有方法复杂到要单测 → 提示**提取为独立类**（SRP 信号）。
- **✗ 测框架行为**（"Spring 能不能注入"） → ✓ 那是集成测试的职责，不是单元测试。

> 过度测试的代价：**测试变脆**（重构一改挂一片）、**维护成本高**、**真正重要的用例被淹没**。少而准，胜过多而水。

## antipatterns

- **✗ 把"覆盖率 ≥ 80%"写进 CI 当硬门禁**（不分模块一刀切） → ✓ 覆盖率作报告+趋势监控，关键模块设阈值，胶水代码豁免。
- **✗ 为了凑覆盖率写"无断言"测试**（调一下方法就算覆盖） → ✓ 每个测试必须有行为断言，否则是假绿。
- **✗ 只看数字不看盲区**（"85% 了，收工"） → ✓ 看那 15% 是哪些分支，判断是漏测还是死代码。
- **✗ 追求 100% 行覆盖** → ✓ 100% 行覆盖 ≠ 无 bug，且边际成本陡增；分支覆盖 + 等价类齐全更实际。
