# 05 · 写多少：覆盖率反向校验 + 成本收益

## 覆盖率的定位

| | 说明 |
|---|---|
| ✗ **不是充分条件** | 100% 行覆盖可能 0% 输入覆盖——`if (x > 0)` 被一个 `x=5` 跑过即"覆盖"，但 `x=0`、`x=-1`、`x=MAX_VALUE` 这些等价类都没测。 |
| ✗ **不是目标** | 追"80% 覆盖率"催生无脑凑数测试（测 getter/setter），数字好看无价值。 |
| ✓ **是反向诊断** | 设计完黑盒用例后，看哪些分支/行**没被覆盖**——那些是"设计漏了"或"死代码"的信号。 |

## 四种覆盖率粒度（由弱到强）

| 粒度 | 含义 | 说明 |
|---|---|---|
| **行覆盖** | 每条可执行语句被执行过 | 最弱。`if(x>0)` 跑一次即覆盖，不管 x 正负。 |
| **分支覆盖**（C1） | 每个分支的 true/false 都走过 | 比 行覆盖 强：`if` 的两边都要测。 |
| **路径覆盖** | 所有执行路径组合 | 最强但通常不可达（组合爆炸），实战不追求。 |
| **MC/DC** | 条件组合中每个子条件独立影响结果 | 航空/安全级才用，普通业务测试不必。 |

**实战基准：以分支覆盖（C1）为校验口径**，行覆盖作辅助。JaCoCo 默认报告同时给两者。不要追求路径覆盖。

## 反向校验流程（覆盖率如何指导设计）

```
1. 先用黑盒方法设计用例（等价类/边界值/决策表/状态）   ← 正向设计
2. 跑测试，看覆盖率报告
3. 找未覆盖的分支/行：
   ├─ 是"应测但漏了"的分支 → 补对应等价类/边界用例      ← 覆盖率补盲区
   └─ 是"不可能进入"的死代码  → 标记，提示用户清理
4. 不要反过来：照着分支表逐个补用例凑覆盖率            ← 白盒驱动，本末倒置
```

### 关键：覆盖率是"设计完整性"的体检，不是设计本身

✗ 错误流程：打开覆盖率报告 → 发现 `line 42` 没覆盖 → 随便写个用例让它执行 → 覆盖率 +1%。这是**用覆盖率驱动设计**，结果是一堆"执行了但没断言关键行为"的废测试。
✓ 正确流程：黑盒设计 → 覆盖率报告暴露盲区 → 思考"这个分支对应哪个等价类/边界" → **补一个有断言的设计用例**。

## JaCoCo 接入（仅项目未有时，且用户问及覆盖率才提）

Spring Boot 项目 `spring-boot-starter-parent` 内置 JaCoCo profile，加插件即可：

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.12</version>
    <executions>
        <execution>
            <goals><goal>prepare-agent</goal></goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>test</phase>
            <goals><goal>report</goal></goals>
        </execution>
    </executions>
</plugin>
```

`mvn test` 后看 `target/site/jacoco/index.html`。**仅当用户问"覆盖率/测够没/接入 jacoco"且项目无时才提**——普通设计用例不必主动推接入。

> **坑：测试不过时报告不生成。** 上面 `report` execution 绑在 `test` phase，任一测试失败 BUILD FAILURE 会中断它，拿不到报告。确需"失败也出报告"用于排查时，把 `<phase>test</phase>` 改成 `verify`，或单独 `mvn jacoco:report` 强制生成。

## "写多少"的成本收益判断

不要把所有方法一视同仁。用 **变更频率 × 业务风险** 决定投入：

```
                    业务风险
              低 ─────────────── 高
         高 │  适度测试          │  重点测试（结算/订单/支付/权限）
变更频率     │  （核心路径+边界） │  （全等价类+全边界+决策表）
         低 │  轻量测试          │  关键测试（金额/异常路径）
             │  （happy+1边界）  │  其余靠类型与编译保障
```

### 该重点测（多投用例）

- **涉及钱的**：金额计算、折扣、结算（off-by-one 即资损）。
- **对外契约**：API 入参校验、对外开放接口。
- **高频变更**：最近 3 个月改动多的方法（回归价值高）。
- **复杂分支**：嵌套 if/switch 多条件 → 用决策表覆盖所有组合。

### 可轻量测（少投用例）

- 纯 POJO 的 getter/setter（不值得测，Lombok 生成更可靠）。
- 框架胶水代码（`@RestController` 转发到 Service，逻辑在框架里）。
- 极少变更且低风险的工具方法（happy path + 一个边界足矣）。

## 什么时候算"够了"——三个停止信号

可勾选的判定 checklist 见 SKILL.md「测试完成判定（DoD 锚点）」（四维度齐全 / 分支覆盖无盲区 / 等价类清单已显式走完，三条同时满足）。本节只记锚点未承载的一个判定陷阱：

- **"无遗漏"不可绝对证明**（等价类是开放集——未来需求演进会带来新输入）。所以"等价类清单已显式走完"这一项判定的对象是**"是否走完了列类 + 打勾的流程"**，而非"是否真的穷尽了一切"——后者只能靠后续 bug / 需求演进时持续补充。不要为追求"100% 等价类"而硬凑变体，那是同质冗余、价值递减。

## 遗留代码：先特征测试锁现状，再小步重构

零测试覆盖的老代码（static 满地、依赖 `new` 死、私有方法塞逻辑、无接口）**不能直接套四维度设计**——设计前提是"能控制输入、能注入依赖"，而遗留代码恰恰锁死了这些。

**解法顺序固定**（characterization test 路线）：

1. **特征测试锁现状**：不设计、不判断对错，把**当前实际输出**录下来当期望值（`assertEquals(currentActual, service.doX(input))`）。目的是建安全网——重构时一旦行为变了，测试立刻红。
2. **小步重构消除"测不了"的根因**：`new` 依赖 → 构造器注入；静态调用 → 接口注入（见 06）；私有方法塞逻辑 → 提取为独立类。每步重构后跑特征测试确认行为不变。
3. **再补四维度设计用例**：依赖可控后，回到 01-04 的正常设计流程。

**切片策略**：按本文「成本收益」矩阵挑**变更频率 × 业务风险**最高的单方法先做闭环，不一次覆盖大类。

> 严重超标方法（认知复杂度 ≥~30）的重构同样要求"先特征测试再拆解"，见 `java-coding-guide-pro/references/12-complexity.md`。
>
> **禁止 PowerMock / 反射强 mock** 绕过 `final`/`static`/`new`——掩盖耦合且让测试更脆；根因治本靠注入重构（见 06 §3）。

## antipatterns

- **✗ 把"覆盖率 ≥ 80%"写进 CI 当硬门禁**（不分模块一刀切） → ✓ 覆盖率作报告+趋势监控，关键模块设阈值，胶水代码豁免。
- **✗ 为了凑覆盖率写"无断言"测试**（调一下方法就算覆盖） → ✓ 每个测试必须有行为断言，否则是假绿。
- **✗ 只看数字不看盲区**（"85% 了，收工"） → ✓ 看那 15% 是哪些分支，判断是漏测还是死代码。
- **✗ 追求 100% 行覆盖** → ✓ 100% 行覆盖 ≠ 无 bug，且边际成本陡增；分支覆盖 + 等价类齐全更实际。
