# 01 · 设计纪律：四维度、黑盒优先、测多少

> 根文件，设计用例前必读。设计方法速查（等价类/边界值/决策表/状态迁移）见 `02`。

## 两条可执行原则

1. **补测场景先逆向还原**：等代码写完再补测试时，先逆向还原被测方法的输入空间与规则，再设计——而非照实现分支凑用例。
2. **高风险域多投用例（Pareto）**：80% 的 bug 集中在 20% 的代码——复杂分支、高风险域（金额/日期/并发/加密）多分配用例。是否涉及钱/对外决定加码深度。

## 四维度模型：每个方法的必检清单

| 维度 | 测什么 | 设计方法 | 落地 |
|---|---|---|---|
| **正向** | 合法、正常输入的预期输出 | 有效等价类代表 | `assertEquals` |
| **反向** | 非法、异常输入的拒绝行为 | 无效等价类代表 | `assertThrows` |
| **边界** | 区间端点、空/null、极值 | 边界值分析 | `assertEquals` |
| **异常** | 业务异常/受检异常抛出路径 | 异常等价类 | `assertThrows` |

> 反向和异常维度是**最常漏**的。只写"传正常值返回正常结果"的测试是 happy path 复读机。例：`divide(a,b)`——正向 `divide(10,2)==5`；反向 `divide(10,0)` 抛异常；边界 `divide(0,5)`、`divide(MAX_VALUE,1)`。四维度是四个视角的检视清单，某些方法会重叠（反向=异常），关键是**四个视角都想过一遍**，不是机械凑四个用例。

## 黑盒视角：只看输入输出，不看实现

- ✗ 先读实现里有哪些 if 分支，再照着分支补用例 → 白盒跟着代码走，代码错了测试也跟着错。
- ✓ 先从接口签名、业务规则推导**应有的输入输出契约**，设计用例，再用覆盖率反向校验盲区。

## 覆盖率立场（一句话）

要求**分支盲区清零**：每个被测方法的每个 `if/switch` 分支至少被一个用例走到——DoD 硬项，与有无工具、用户是否问及无关。**不设任何覆盖率百分比**：80% 行覆盖既不必要（测 getter 可凑出）也不充分（`if(x>0)` 跑一个 `x=5` 即"行覆盖"，`x=0`/`x=-1` 等价类仍全空）。以**分支覆盖（C1）**为校验口径，不追求路径覆盖/MC/DC。

**反向校验流程**：黑盒设计用例 → 跑测试看覆盖率报告 → 未覆盖的分支，是"应测但漏了"→ 补对应等价类/边界用例；是"不可能进入"→ 标记死代码提示清理。**不要反过来照分支表凑用例**——那是用覆盖率驱动设计，产出无断言关键行为的废测试。

## JaCoCo 接入（用户问覆盖率时才给方案）

盲区核对**不依赖工具**——人工分支清单是默认路径。仅当用户问且项目无 JaCoCo 时给接入：

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version><!-- 现场填当前最新稳定，勿照抄旧教程数字 --></version>
    <executions>
        <execution><goals><goal>prepare-agent</goal></goals></execution>
        <execution><id>report</id><phase>test</phase><goals><goal>report</goal></goals></execution>
    </executions>
</plugin>
```

两个坑：① `<version>` 建议显式写——留空时 Maven 解析最新 release 并告警（`spring-boot-starter-parent` 的 pluginManagement **不**管理 jacoco 版本）；② `report` 绑 `test` phase 时任一测试失败则报告不生成——确需失败也出报告，把 phase 改 `verify` 或单独 `mvn jacoco:report`。`mvn test` 后看 `target/site/jacoco/index.html`。

## "写多少"：成本收益判断

用**变更频率 × 业务风险**决定投入，不平均用力：

| | 业务风险低 | 业务风险高 |
|---|---|---|
| **变更频率高** | 适度（核心路径+边界） | 重点（全等价类+全边界+决策表） |
| **变更频率低** | 轻量（happy+1 边界） | 关键（金额/异常路径） |

- **重点测**：涉及钱的（off-by-one 即资损）、对外契约（API 入参校验）、最近 3 个月改动多的、嵌套 if/switch 多条件的。
- **轻量/不测**：Lombok POJO getter/setter、框架胶水、极少变更低风险的工具方法。

## 三个停止信号

- **"无遗漏"不可绝对证明**（等价类是开放集）——DoD 判定的对象是"是否走完了列类+打勾的流程"，不为"100% 等价类"硬凑变体（同质冗余、价值递减）。
- 四维度齐全 + 分支盲区清零 + 等价类清单走完（SKILL.md DoD 锚点三条）同时满足 → 这个方法停手。
- 端点级：每端点 1~3 条本地接口用例（见 `03`）→ 这个端点停手。

## 遗留代码：先特征测试锁现状，再小步重构

零覆盖老代码（static 满地、依赖 `new` 死）**不能直接套四维度**——设计前提"能控制输入、能注入依赖"被锁死。顺序固定：

1. **特征测试锁现状**：把当前实际输出录下来当期望值（`assertEquals(currentActual, service.doX(input))`），建安全网。
2. **小步重构消除测不了的根因**：`new` 依赖 → 构造器注入；静态调用 → 接口注入（`04` §3）；每步跑特征测试确认行为不变。
3. **再补四维度设计用例**。

**禁止 PowerMock / 反射强 mock** 绕过 `final`/`static`/`new`——掩盖耦合且更脆。认知复杂度 ≥~30 的方法判"严重超标"，同样先锁现状再拆。

## antipatterns

- **✗ "覆盖率到了 80% 就行"当唯一标准** → ✓ 覆盖率是反向诊断不是目标；100% 行覆盖可能 0% 输入覆盖。
- **✗ 照着实现里的 if 分支补用例** → ✓ 黑盒先于白盒：先契约推导，再覆盖率反向校验。
- **✗ 把"覆盖率 ≥ 80%"写进 CI 当一刀切门禁** → ✓ 团队既有此门禁：照做但设计标准不降；从零定策略：仅对"重点测试"象限设**分支覆盖**阈值，胶水/POJO 豁免。
- **✗ 为凑覆盖率写无断言测试** → ✓ 每个测试必须有行为断言，否则是假绿。
