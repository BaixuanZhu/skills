# 01 · 测试设计思想基础

> 本技能的根文件。所有具体设计方法（等价类/边界值/决策表/状态迁移）都建立在本文件的思想上。**设计用例前必读。**

## 核心立场：测什么 > 怎么测

测试质量的决定因素是**用例设计**（测哪些、测多少），不是 API 调用方式（`assertEquals` 怎么写）。后者查文档 30 秒可得，前者是开发者普遍缺失、AI 普遍给不好的能力。

```
价值排序：选对"测什么"  >>  选对"用什么方法设计"  >>  选对"调哪个 API"
                  ↑                              ↑                  ↑
            本技能的核心            02-05 文件             06 文件（最薄）
```

## 为什么不能"想到哪测到哪"

随机补测（想到一个写一个）的本质问题是**不可视、不可校验、必有盲区**：

- **不可视**：你不知道已经覆盖了哪些输入空间、还漏哪些。系统方法（等价类）能把输入空间显式列出来。
- **不可校验**：没法回答"测够了吗"。覆盖率工具只能告诉你"代码行执行了没"，不能告诉你"输入空间覆盖了没"。
- **必有盲区**：人脑倾向于测正常路径（happy path），而 bug 90% 在边界和异常路径。

> **杀虫剂悖论（ISTQB）**：同样的用例反复跑，发现新 bug 的能力会衰减到零。测试集必须随被测代码演进持续补充新的等价类与边界——这是"持续设计"，不是"一次性补齐"。

## 四个 ISTQB 根原则（贯穿所有设计方法）

1. **穷尽测试不可能**：输入空间通常无限（所有字符串、所有金额、所有日期组合）。目标不是全测，而是**用等价类把无限压成有限代表**，用边界值钉住高风险点。
2. **测试尽早介入**：等代码写完再补测试，设计空间已被实现锁死（依赖耦合、分支写死）。理想是"设计先行"——但本技能面对的多数是**补测试**场景，因此退而求其次：补测时先逆向还原被测方法的输入空间与规则，再设计。
3. **聚类缺陷（Pareto）**：80% 的 bug 集中在 20% 的代码——复杂分支、高风险域（金额/日期/并发/加密）。设计用例时，这 20% 要多分配用例，不是平均用力。
4. **测试活动依赖上下文**：金融结算和内部 admin 工具的测试深度要求不同。本技能给"最小充分集"，再由业务上下文（是否涉及钱、是否对外）决定加码。

## 四维度模型：每个方法的必检清单

任何被测方法，**至少**回答这四组"有没有测到"——缺一个维度就是设计漏洞：

| 维度 | 测什么 | 设计方法 | 落地 |
|---|---|---|---|
| **正向** | 合法、正常输入的预期输出 | 有效等价类代表 | `assertEquals` |
| **反向** | 非法、异常输入的拒绝行为 | 无效等价类代表 | `assertThrows` |
| **边界** | 区间端点、空/null、极值 | 边界值分析 | `assertEquals` |
| **异常** | 业务异常/受检异常抛出路径 | 异常等价类 | `assertThrows` |

> 反向和异常维度是**新手最常漏**的。只写"传正常值返回正常结果"的测试，本质是 happy path 的复读机，测不出任何 bug。

### 一个具体例子：`divide(int a, int b)` 的四维度

```
被测：double divide(int a, int b)   返回 a/b

正向：divide(10, 2) == 5.0           有效等价类代表
反向：divide(10, 0)                  无效等价类 → 抛 ArithmeticException（或业务异常）
边界：divide(0, 5) == 0.0            分子为 0 的边界（0 是边界值）
      divide(Integer.MAX_VALUE, 1)   极大值边界（防溢出/精度）
异常：除数为 0 的异常路径已含在"反向"——此例反向=异常，正常
```

四维度不是"必须互斥的四类"，而是"四个视角的检视清单"。某些方法四维度会重叠（如上例反向=异常），关键是**四个视角都想过一遍**，而不是机械凑四个用例。

## 黑盒视角：只看输入输出，不看实现

设计测试用例时**优先用黑盒视角**（规格/接口契约），不要先钻进实现：

- ✗ 先读实现里有哪些 if 分支，再照着分支补用例 → 这是**白盒跟着代码走**，代码错了测试也跟着错（测试只是确认"代码做了它做的事"，而非"代码做了对的事"）。
- ✓ 先从接口签名、注释、业务规则推导**应有的输入输出契约**，设计用例，再用实现来校验覆盖率盲区。

> 白盒覆盖率的正确用法是**反向校验**（见 05）：设计完黑盒用例后，看哪些分支/行没被覆盖，那些是"设计漏了"或"死代码"的信号——而不是反过来"照分支写用例"。

## 什么算一个"好"的单元测试（FIRST + 一个关注点）

- **F**ast：毫秒级，不起外部容器（这是它区别于集成测试的根本）。
- **I**solated：不依赖其他测试的执行顺序或遗留状态。
- **R**epeatable：跑 N 次结果一致（特别注意时间、随机数——mock 掉或注入固定值）。
- **S**elf-validating：断言明确，pass/fail 一目了然，不需要人工看输出。
- **T**imely：尽早写（理想是先于实现；补测场景至少在重构前补齐）。
- **一个测试验证一个行为**：可以多个断言，但必须围绕同一关注点；失败时能一眼定位。

## 本技能的方法选择决策树

```
被测方法是什么样？
│
├─ 纯输入→输出（计算/校验/格式化）
│    → 02 等价类 + 边界值（最高频，80% 场景）
│
├─ 多个条件组合决定结果（促销规则/费率/权限矩阵）
│    → 03 决策表（列数=用例数，防组合遗漏）
│
├─ 对象有状态，行为依赖当前状态（订单/审批/支付）
│    → 04 状态迁移（合法转移 + 非法转移拒绝）
│
└─ 不知道"写多少算够"
     → 05 覆盖率反向校验 + 成本收益判断
```

多数情况从 02 开始。03/04 是 02 在特定结构上的特化方法。05 是所有方法的质量校验层。

## antipatterns

- **✗ "覆盖率到了 80% 就行"当唯一标准** → ✓ 覆盖率是必要不充分条件，见 05。100% 行覆盖可能 0% 输入覆盖。
- **✗ 照着实现分支补用例** → ✓ 黑盒先于白盒，分支覆盖只做反向校验。
- **✗ 测试名 `testDivide1`/`testDivide2`** → ✓ `should_returnQuotient_when_twoPositiveNumbers`，名字即规格。
- **✗ 一个测试方法里既测正常又测异常** → ✓ 拆成 `should_..._when_valid` 与 `should_throw_..._when_invalid`。
- **✗ 测了 20 个用例但全是同一个等价类的变体**（如 20 个不同的正整数相除）→ ✓ 等价类内取一个代表，省下的额度去测其他等价类（0、负数、除数为 0、极值）。
