# 假绿陷阱（按失效模式分组）

只收**写错了不报警**的：编译过、启动过、测试甚至全绿，线上却丢消息、重复执行或积压。
会红的（依赖缺失、API 签名错）不在此处。每条结构：**为什么绿 → 改法 → 怎么验证**。

用法是拿问题去追代码路径，不是逐组扫表。某组零命中或不适用，在结论里写明
「第 N 组不适用，因为……」——跳过的决定不出现在输出里，与「代码没问题」无法区分。

## 组一 消息静默消失

1. **DLQ 配了没人看**
   为什么绿：消息正常消费时一切正常；出问题的消息进死信队列后无人知晓，
   比不配 DLQ 更糟——不配至少会阻塞队列被人发现。
   改法：DLQ 挂消费者（告警 / 补偿 / 人工处理）或队列深度告警（> 0 即通知）。
   验证：手动往 DLQ 投一条消息，确认告警触发或消费者收到。

2. **publisher confirm 未开**
   为什么绿：开发环境 broker 稳定，消息都能到；生产环境网络抖动或 broker 重启，
   消息静默丢失，发送方毫无感知。
   改法：`publisher-confirm-type: correlated` + ConfirmCallback 处理 nack；
   `publisher-returns: true` + `template.mandatory: true` + ReturnsCallback。
   验证：停掉 broker 再发送，确认回调触发告警。

3. **mandatory 未开，不可路由消息静默丢弃**
   为什么绿：路由键配对时一切正常；配错时消息被 broker 直接丢弃，无任何报错。
   改法：`template.mandatory: true` + ReturnsCallback。
   验证：故意发一个不匹配任何队列的路由键，确认收到退回回调。

## 组二 重复副作用

4. **累加型操作裸消费**
   为什么绿：select → score+1 → update，测试只投一次跑得完美；
   重复投递时比分翻倍，测试永远不会投两次。
   改法：业务唯一键去重（DB 唯一索引 / Redis setnx）后才累加；或 sequenceNo 状态机。
   验证：同一条消息手动投两次，确认比分只加一次。

5. **委托下游去重但下游没做**
   为什么绿：注释写了「下游自行去重」，代码看起来没问题；
   下游根本没实现去重，用户收到两条一样的通知。
   改法：自己去重，或与下游**书面约定**去重键和语义（不是写注释）。
   验证：同一条消息投两次，确认下游只产生一次副作用。

6. **多步副作用 + AUTO ack + JVM crash**
   为什么绿：单次消费跑通一切正常；第 1 步发了通知、第 2 步写 DB 前 JVM 崩了，
   消息重投后第 1 步重复执行。
   改法：多步副作用用手动 ack（全部成功才 ack）；或保证幂等后 AUTO 可接受。
   验证：在第 1 步后抛异常模拟 crash，确认重投后第 1 步不重复。

## 组三 顺序错乱

7. **不问顺序就开多消费者**
   为什么绿：功能测试每个消费者独立跑都对；多消费者抢同一队列时
   先发的事件可能后处理，状态机流转错乱。
   改法：先答 D4。要顺序 → 单消费者，或按业务键分片 + `x-single-active-consumer`。
   验证：并发发 100 条有序事件，确认处理顺序与发送顺序一致。

8. **prefetch > 1 时重投乱序**
   为什么绿：正常消费顺序没问题；第 3 条失败重投时，
   prefetch 拉到的第 4~10 条可能已处理完，第 3 条反而排在后面。
   改法：要顺序就 prefetch 设 1~10；或应用层用序号拒绝乱序（gap 检测）。
   验证：让第 3 条消费失败一次，确认最终状态与顺序消费一致。

## 组四 积压失控

9. **无队列深度监控**
   为什么绿：测试几条消息瞬间消费完；高峰期生产速率是消费的 10 倍，
   队列积压到 10 万条才被用户投诉发现。
   改法：队列深度告警阈值 + 消费 / 生产速率对比。
   验证：灌 1 万条消息不消费，确认告警触发。

10. **prefetch 未设或照抄**
    为什么绿：默认值（250）在测试环境没问题；生产环境单条消息体大时
    250 条 prefetch 撑爆消费者内存，或单条处理慢时吞吐上不去。
    改法：按「单条消费耗时 × 期望吞吐」定 prefetch，不是照抄默认值。
    验证：压测时观察消费者内存和吞吐。

## 框架默认值速查（Spring AMQP）

| 配置项 | 默认值 | 问题 |
|---|---|---|
| `publisher-confirm-type` | NONE | 发送方不知道消息丢了 |
| `listener.simple.acknowledge-mode` | AUTO | 多步副作用 crash 后重复执行 |
| `template.mandatory` | false | 不可路由消息静默丢弃 |
| `listener.simple.default-requeue-rejected` | **true** | 毒消息无限循环 |
| `listener.simple.prefetch` | 250 | 可能撑爆内存 |

前三个是陷阱，第四个模型本能会处理但仍需确认，第五个看场景。
