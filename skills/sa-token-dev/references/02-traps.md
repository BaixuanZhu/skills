# 假绿陷阱（按失效模式分组）

只收**写错了不报警**的：编译过、启动过、测试甚至全绿，鉴权却失效或行为退化。会红的（starter 冲突、
API 签名错）不在此处——报错本身就会被发现。每条结构：**为什么绿 → 改法 → 怎么验证**。

用法是拿问题去追代码路径，不是逐组扫表。某组零命中或不适用，在结论里写明「第 N 组不适用，因为……」——
跳过的决定不出现在输出里，与「代码没问题」无法区分。

## 组一 收口失效：鉴权声明了，但没在请求路径上

1. **注解没有 SaInterceptor 兜着**
   为什么绿：`@SaCheck*` 静默不解析，所有请求直通，应用一切正常直到被打穿。
   改法：注册 `SaInterceptor` 并覆盖对应路径；新增受保护接口后确认它落在拦截范围内。
   验证：不带 token 调该接口，必须被拦；返回业务数据 = 注解没生效。

2. **StpInterface 缺失 / 漏 @Component**
   为什么绿：权限数据源为空时所有 `checkPermission`/`checkRole` **静默通过**。
   改法：实现 `StpInterface` 并纳入 Spring 容器；权限码从真实数据源取。
   验证：给一个不含该权限码的账号调接口，必须 403；通过 = 数据源没接上。

3. **两套白名单并存（@SaIgnore + SaRouter.free）**
   为什么绿：两边各自正确，合起来漏——注解放行的路由侧可能拦（反之亦然），谁先执行看注册顺序。
   改法：白名单只维护一处；混用时注解侧 `@SaIgnore`、路由侧 `free()` 各自只出现一次，路径清单同源。
   验证：白名单里的路径逐个手动请求确认放行，白名单外一个路径确认被拦。

4. **SaRouter 顺序错**
   为什么绿：`match` 按书写顺序，先命中的 `stop()` 短路；放行规则写在拦截规则之后 = 永远不生效，反之放行形同虚设。
   改法：宽路径拦截在前、窄路径放行在后（或明确 `free()` 的语义边界），写完在注释里标明顺序依赖。
   验证：构造一个「该拦」与「该放」的边界路径各请求一次。

5. **网关校验了，下游直接信透传头**
   为什么绿：开发期所有流量都过网关，一切正常；直连下游端口即可冒充任意用户。
   改法：下游对不可信来源二次验签，或网络层保证下游不可直连。
   验证：绕过网关直接带伪造头请求下游，必须被拒。

## 组二 状态语义：命令发出了，但没作用到目标 token

6. **封禁不用内置 API（实测最高频的能力缺失）**
   为什么绿：自造「内存 Map + 登录时拦截」跑起来完全正常，但重启即失效、多实例不一致、
   在线用户不掉线、与框架的 DISABLE 语义完全脱节。
   改法：`StpUtil.kickout(id)` → `StpUtil.disable(id, time)`，登录前 `StpUtil.checkDisable(id)`
   （v1.31.0+ `login()` 不校验封禁）。解封 `enable(id)`。
   验证：封禁后旧 token 立刻不能访问 + 被封账号登录被拒，两条都要验。

7. **kickout / replaced / logout 三种下线混用**
   为什么绿：三种都「让 token 失效」，功能上看不出差别，前端提示语义错乱才发现。
   改法：`logout` 正常注销；`kickout` 管理端强制下线（场景值 KICK_OUT）；`replaced` 同端顶下线
   （BE_REPLACED）。按 `NotLoginException.getType()` 分支给不同提示。
   验证：三种下线各触发一次，确认前端收到的场景值可区分。

8. **is-share=true 时想按设备踢人**
   为什么绿：配置合法、登录正常，kickout 一踢所有端一起掉——共享 token 无从区分设备。
   改法：要按设备管理就 `is-share=false` + `is-concurrent=false` + `login(id, device)`。
   验证：两台设备登录后踢一台，另一台必须不受影响。

9. **active-timeout 的语义误读**
   为什么绿：它不是「总有效期」而是「最低活跃频率」——超时**冻结**（不是删除），活跃即自动续签。
   配了它却以为没配，用户隔周回来「莫名」要重登。
   改法：产品要「30 天免登录」就只配 `timeout`，别配 `active-timeout`；要「7 天不活跃就掉线」才配它。
   验证：把 active-timeout 临时调成 10 秒，静置后请求确认被冻结、活跃后又可用。

10. **JWT Simple 模式下 is-share 恒为 false**
    为什么绿：配置文件里写了 `is-share: true` 不报错但不生效，行为与预期分叉。
    改法：用 JWT Simple 就接受「每次登录都是新 token」；要共享 token 回 simple-uuid。
    验证：同账号连续登录两次拿 token，Simple 下两次值不同。

## 组三 能力缺失：方案选型时丢掉的能力，后期才发现要

11. **Stateless / SaJwtUtil 直连后才要踢人**
    为什么绿：签发验签一切正常，直到运营要「强制下线某用户」——无服务端状态可作废。
    改法：选型时对照 `01-decisions.md` §1 能力矩阵；要踢人就别选无状态。已选无状态的替代手段只有
    短有效期 + 刷新令牌，别对用户承诺「支持踢人」。
    验证：承诺过的能力逐个真调一次（kickout / getSession / disable），做不到就改承诺。

12. **SaSession 与 HttpSession 混用**
    为什么绿：两者 API 相似，写 `request.getSession().setAttribute` 存、`StpUtil.getSession().get` 取，
    取到 null 还以为是缓存过期。
    改法：全程 `StpUtil.getSession()`（Account/Token/Custom 三种作用域按 key 归属选）。
    验证：存取走同一入口后加一条断言；logout 后 Token-Session 应随之清理，Account-Session 留存。

13. **多体系用单体系 API**
    为什么绿：`StpUtil` 默认操作主体系，商家端登录写进 `StpUtil.login` 后用户端能读到商家会话。
    改法：≥2 套体系用 `StpKit.of("merchant")` 一套独立 StPLogic；体系标识启动期定死（见组五 18）。
    验证：两个体系各登录一次，确认 token 互认失败。

## 组四 请求通道：凭证传不对，鉴权时好时坏

14. **前后端分离登录响应不带 tokenValue**
    为什么绿：后端登录逻辑正确、自测用 Cookie 通过；App/SPA 拿不到凭证，表现为「登录成功但下一步未登录」。
    改法：Header 模式登录响应返回 `tokenName + tokenValue`（或 `SaTokenInfo`）。
    验证：模拟无 Cookie 客户端完整走一遍登录 → 带 header 请求受保护接口。

15. **SaServletFilter 异常不进 @ExceptionHandler**
    为什么绿：Controller 层异常处理写得很全，过滤器抛的异常绕过它直接 500 / 默认错误页。
    改法：`SaServletFilter` 必须 `.setError(e -> ...)`；能用 `SaInterceptor` 就别用 Filter（拦截器异常
    走 Spring 异常处理链）。
    验证：过滤器鉴权路径下发起未登录请求，确认收到的是约定 JSON 而不是 500。

16. **token 前缀/空白处理**
    为什么绿：`Authorization: Bearer  xxx`（双空格）或前缀配置与前端不一致，验签失败表现为随机未登录。
    改法：前后端约定前缀格式；服务端 `token-prefix` 配置与前端拼接严格一致，解析时 trim。
    验证：用前端真实格式的 header 验一次，别用 Postman 手敲的。

17. **反向代理后 uri 变了**
    为什么绿：本地直连一切正常，上线后路由匹配全失效——SaRouter 拿到的是代理改写后的 uri。
    改法：网关/代理保留原始 uri（`X-Forwarded-Prefix` 等），或按改写后路径写规则。
    验证：带代理前缀的路径手验一条拦截规则。

## 组五 配置与集成：默认值/并发/生命周期

18. **多账号 LoginType 运行期修改**
    为什么绿：`StpUtil.TYPE` 之类的体系标识运行中改掉，行为未定义但不报错。
    改法：体系标识启动期定死（枚举/常量），要多体系用 StpKit 显式建。
    验证：代码里 grep 体系标识赋值处，确认只有启动期写入。

19. **Same-Token 多服务并发刷新**
    为什么绿：单服务测试通过；多服务同时启动/刷新内部标识，出现瞬时内部调用失败。
    改法：内部标识由一处签发（或网关统一分发），不要各服务各自刷。
    验证：多实例同时重启一次，观察内部调用错误率。

20. **全局侦听器/过滤器未兜异常**
    为什么绿：侦听器里抛出的异常不会打断主流程，但会中断后续侦听器——数据缺失查不到原因。
    改法：`SaTokenEventCenter` 侦听器内部自己 try-catch + 日志。
    验证：在侦听器里故意抛一次，确认主流程存活且日志有记录。

21. **SSO allow-url 配 `"*"`**
    为什么绿：登录跳转一切正常，等于任何回调地址都能换 Ticket——开放重定向漏洞。
    改法：allow-url 逐个列可信回调域。
    验证：用伪造回调地址走一遍换票流程，必须被拒。

22. **SSO 模式一 Cookie domain 残留**
    为什么绿：同域共享 Cookie 场景，切换账号后旧 Cookie domain 未清理，串号。
    改法：登出时清理所有涉及子域的 Cookie。
    验证：A 登出 → B 登录，确认 B 的请求不带 A 的残留凭证。

23. **跨域 + Cookie 通道**
    为什么绿：后端鉴权正确，浏览器跨域不带 Cookie，表现为「接口时好时坏」。
    改法：跨域要么 CORS 配 `allow-credentials` + 前端 `withCredentials`，要么切 Header 通道（`01-decisions.md` §3）。
    验证：从真实前端域名发请求确认凭证携带。
