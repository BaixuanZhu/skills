# Backlog 规则（agile-backlog 参考）

## 一、ID 命名约定

| ID 前缀 | 含义 | 示例 |
|---------|------|------|
| `T-NNN` | 技术任务（Technical） | T-001 工程初始化 |
| `F-NNN` | 功能需求（Feature） | F-001 运营登录 |

**不再使用** US（用户故事）/ EN（使能项）/ EPIC 命名——避免概念混淆。技术任务与功能需求**平级**进入待办池。

## 二、字段定义

每个 backlog 条目在排序表中占一行，字段如下：

| 字段 | 必填 | 说明 |
|------|------|------|
| ID | ✅ | T-NNN 或 F-NNN，零填充 3 位 |
| 标题 | ✅ | 一句话概括（动词 + 名词） |
| 类型 | ✅ | 技术 / 功能 |
| 仓库 | — | 条目归属仓库（多仓库项目标注，如 `api-server`；单仓库项目留空） |
| 点 | ✅ | 斐波那契（1/2/3/5/8/13，默认）；纯研究型 Sprint 可用线性（1/2/3/4/5），在 Sprint 文件头标注；过大无法估点 → 触发边界异常 ⑤（拆分） |
| 优先级 | ✅ | Must / Should / Could / Won't |
| 状态 | ✅ | 待办 / 已完成 / 已撤回 |
| 关联 | — | ADR 编号（如 ADR-006）或依赖条目 ID；无则"—" |
| 来源/依据 | — | 点的来源（agent 推荐 / 用户确认）+ 优先级依据（开发顺序 / MoSCoW / 依赖 / ADR 优先级） |
| 已确认 | ✅ | `✓`（优先级/点数/验收已与用户确认）/ `待确认`（agent 推荐，Sprint 取用前必须显式转 ✓，见 §五） |

## 三、优先级排序逻辑

1. **开发顺序（用户指定）**：按用户口述的先后顺序（先做 A、再做 B）
2. **业务优先级（MoSCoW）**：Must > Should > Could > Won't
3. **依赖关系**：被依赖项优先于依赖项（如 T-001 工程初始化必须先于 T-002 引入 ArchUnit）。**跨仓库依赖**（不同仓库条目有先后开发关系，如后端接口 → 前端页面）在 Sprint 规划时声明「交接契约」（见 `agile-sprint/references/sprint-template.md` §交接契约），Backlog 层只体现排序
4. **架构约束**：关联 ADR 的 T-NNN 按 ADR 优先级排

## 四、展开规则

判定"非显然"的客观标准（满足任一即需在底部"任务详情"区展开）：

- **验收标准非显然**：条目交付后用户/系统可观察的行为不能从标题直接推出
  - 示例："F-002 审核身份升级" → 展开"5 种身份申请单 / 营业执照校验 / 通过则附加身份到账号"
- **约束非显然**：条目受特定技术或业务约束
  - 示例："T-003 后台管理与用户端访问隔离" → 展开"两套登录态互不影响 / 管理端仅内网可达 / 关联 ADR-002"
- **关联非显然**：条目依赖其他条目或外部系统
  - 示例："T-010 Stripe 集成" → 展开"3DS / Webhook / 仅 SaaS 订阅场景"

判定"显然"（无需展开）：标题 + 点数 + 关联字段已完整表达意图。

**展开格式**：3-5 行 bullet，覆盖验收 / 约束 / 关联即可。**禁止**写成完整用户故事格式（INVEST / Given-When-Then 仪式不要）。

### 范围 vs 实现（写入边界）

Backlog 是给消费 Agent 定**范围**（做什么），不是定**实现**（怎么做）——实现规划由消费 Agent 在代码上下文中判断。

| 写 ✅（范围） | 不写 ❌（实现） |
|---------------|----------------|
| 可观察验收行为 | 技术方案 / 框架选型 |
| 业务与非功能约束 | 代码结构 / 类与方法设计 |
| 边界（做什么 / 不做什么） | SQL / 伪代码 / 具体 API 调用建议 |
| 依赖关联（条目 / ADR / 外部系统） | "建议做法"式实现细节 |

- 技术决策已在 ADR 拍板 → T-NNN 关联 ADR 章节即可，条目内不展开实现方案
- 反例（✗）：`"双 SecurityFilterChain 场景 → 展开 admin/app 两套分离 / 独立 SecurityFilterChain bean"` —— "独立 bean"即实现建议，应删，只留范围："两套访问控制互不影响"

## 五、状态流转与「可注记不可改写」

```
待办 ─────────────→ 已完成（通过 DoD）
  │
  └─→ 已撤回（不参与排序 / 统计，留痕追溯）
```

**三态枚举**（阶段表「状态」列）：`待办 / 已完成 / 已撤回`

- **待办**：默认状态（含已纳入 Sprint 但未完成——执行态追踪由消费 Agent 负责，不在规范层体现）
- **已完成**：通过 DoD 验收
- **已撤回**：本阶段/本 Sprint 不再需要的条目，从池中摘出不参与排序与统计（全量统计时自动排除），仍留痕可追溯。撤回时追加「撤回时间 / 撤回原因 / 决策来源」，不改写条目原内容

**确认状态**（独立于状态列，对应阶段表「已确认」列）：
- 「已确认」：优先级 / 点数 / 验收已与用户确认 → `✓`
- 「agent 推荐待确认」：未与用户确认 → `待确认`，Sprint 取用前必须显式转 `✓`（agile-sprint 跳过并告警）

Sprint 未完成的条目在 `.done` 同步时 `moved_next → 待办`（不改优先级，自然回到取用顺序前列），**不设「移至下个Sprint」状态**——该表述只出现在 Sprint 文件的「条目状态建议」里，不进 Backlog。

### 已完成条目：「可注记、不可改写」

**已完成条目的事实不可变**（验收行为 / 关联 ADR / 当时决策内容）。后续需要修订时：

- ✅ **追加注记**：在条目下方追加 `> [YYYY-MM-DD] {变更摘要}。**已完成状态不变**。`——明确区分历史事实与后续决策；不篡改交付时快照
- ❌ **改写历史**：删旧验收 / 改点数 / 篡改关联——禁止（审计追溯的基础）
- 例外：用户明确裁决"撤回 / 废止已完成条目"→ 走本节撤回流程（状态 → 已撤回），历史事实仍不删，仅追加注记

惯例来源：评审类裁决影响已交付条目时（如 ADR 替代影响已完成条目的口径），追加注记而非改写历史（见 agile-strategic 门禁② 与 change-matrix.md §四 下游影响评估）。

## 六、门禁

详见 `using-agile/references/gate-protocol.md §二`（① 技术任务须关联 ADR）+ §三 边界异常 ⑤（过大条目拆分后估点）。

## 七、表格机读契约（消费 Agent 读此文件）

文件：`agile-docs/PRODUCT-BACKLOG.md`——**人读与 Agent 共读同一份，不另建机器侧副本**。

**列名严格固定**（消费 Agent 与统计都按死契约解析，不自由增删改列名）：

```
| ID | 标题 | 类型 | 仓库 | 点 | 优先级 | 状态 | 关联 | 来源/依据 | 已确认 |
```

机读约定：

1. 消费 Agent 统一读阶段表获取排序和状态；需要详情时按 id 回读「任务详情」段中对应展开段落
2. 「关联」列中的 ADR 引用保持 `ADR-NNN` 模式（可混依赖条目 ID，解析时按模式提取 ADR 编号；占位符 — / - / 无 视为空）
3. 「已确认」列取值仅 `✓` / `待确认` 两种
4. 「状态」列取值仅 `待办` / `已完成` / `已撤回` 三种
5. **统计规则**：需要条目数 / 点数 / 分组统计时，从阶段表**重新全量统计**（覆盖式重算），禁止在旧统计数字上增量加减

**旧格式迁移**：v4.x 及之前的双文件格式（`PRODUCT-BACKLOG.yaml` / `PRODUCT-BACKLOG.json`）已废弃。检测到旧文件 → 把其中仅机器侧持有的信息（adr_refs / confirmed / withdrawn）核对进阶段表对应列（关联 / 已确认 / 状态），删除旧文件。
