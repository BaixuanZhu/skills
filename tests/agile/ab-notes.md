# agile 5.3.0 / 5.4.0 阶段注入的 AB 实测

测的是 `hook-prompt` 每轮注入那一段到底起什么作用。

## 结论

**注入的作用域严格等于它写下的那句话。** 写进去的漏被防住，没写的等于没写——四组对照：

| 对照项 | 注入里写了吗 | 无注入组 | 有注入组 | 判定 |
|---|---|---|---|---|
| 容量三项必问、禁止静默按 0.6 | 写了 | 0/2 问系数 | 2/2 必问 | 生效 |
| 新需求不改进当前 Sprint | 写了 | 2/2 改写了 sprint 文件 | 0/2 | 生效 |
| 不手改渲染产物 md | 没写 | 2/2 手改 | 1/2 手改 | 无差异 |
| 不新建重复条目 | 没写 | 0/2 新建 | 2/2 新建 | 无差异，有注入组更差 |

第四行是负增量，不是噪声：旧文案「新需求先入 backlog 排序」被理解成「去 backlog 建一个条目」，而正确动作是先比对是否已有条目覆盖。改文案后（5.4.1）复验 2/2 改为补记已有条目。

## 两个条件的差异

- **技能可读**（项目内有 `.claude/skills/`）：两组都做对，注入零增量。技能内容已经够，瓶颈从来不是信息缺失。
- **技能不可读**（模拟插件缓存里 agent 未探索）：只有一行注入，增量出现，但只覆盖注入点到的那条。

推论：注入不替代技能，它替代的是「模型没想到去读技能」这个失败模式。

## fixture

`make_fixture.py` 生成，`sprint` / `active` 两个场景各 2 组。它做三件校验，任何一步失败就退出：

1. 同场景各组文件清单逐一比对（不同场景本来就该不同，所以只在场景内比）
2. 每组 `PRODUCT-BACKLOG.md` 的 sha 指纹与 `backlog.json` 一致
3. 第一阶段条目置 `confirmed=true`，否则 sprint 场景无一条可取，容量问题被掩盖

第 1、2 条是补出来的——初版只给一半目录跑了 `render`，导致「有注入组没手改渲染产物」其实是**那个文件根本不存在**。假通过的形态：被测量对象在对照组里缺位。

```
python tests/agile/ab/make_fixture.py      # 第一轮
python tests/agile/ab/make_fixture.py r2   # 第二轮复验
python tests/agile/ab/make_fixture.py r3   # 改文案后验证
```

生成器从自身位置推导 fixture 源（`../stage/`）与 `agile.py` 路径，产物写进临时目录并打印路径——换机器直接跑。**改 `turn-brief.md` 文案后按本方法论复验**：注入的作用域严格等于写下的那句话，措辞改动必须在有/无注入两组上对照确认方向。
