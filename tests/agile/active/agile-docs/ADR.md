## ADR-001 保持模块化单体，不拆服务

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 单人开发兼运维；日均 1200 单、峰值 9000 单 / 20 分钟（约 8 单/秒均值、峰值不超过 30 单/秒），当前为单进程 + 单库。
- 决策: 维持单体部署，按"下单 / 售后 / 查询 / 对账"划分包边界，不拆服务、不引入服务网格与注册中心。依据: agent 推荐待确认 —— 峰值量级远低于单体承受能力，拆分的确定性收益为零，确定性成本是唯一的维护者要同时运维 N 个进程。
- 后果: + 事务边界简单、部署与排障只有一条路径 / - 包边界靠自觉，几个月后容易退化成"什么都往 service 里塞" / 缓解: 在 CI 中加包依赖检查（ArchUnit），边界破坏时构建失败。

## ADR-002 必须送达的异步副作用走 outbox，不引入 MQ

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 审计用 `@TransactionalEventListener + @Async`（2026-02 决策），进程重启时在途任务丢失，对账已发现两次差额、靠人工补（README 已知问题 5）。
- 决策: 凡"事务提交后必须发生"的副作用（审计、后续的通知与对账事件）统一写同库 outbox 表，由轮询器投递并记录投递状态与重试次数；不引入消息队列。依据: agent 推荐待确认 —— 单库单进程下 outbox 足以提供"不丢 + 可重放"，MQ 换来的是专职运维成本。
- 后果: + 与业务同事务、重启不丢、可重放补数 / - 引入轮询延迟与表膨胀 / 缓解: outbox 按时间归档，投递带幂等键，积压量进监控告警。

## ADR-003 幂等与并发控制交给数据库约束，不引入 Redis

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: `countByOrderNo` 先查后插在并发下穿透，靠唯一索引兜底报 500（已知问题 3）；库存条件扣减在高峰偶发死锁直接 500（已知问题 4）；2026-05 曾考虑 Redis 分布式锁，因"为查重引中间件不值"搁置。
- 决策: 幂等由 `order_no` 唯一约束 + 冲突语义承担（重复提交返回既成结果而非报错）；库存以单条条件更新保证原子性，死锁/序列化失败按有限次退避重试；不引入 Redis 或跨进程锁。依据: agent 推荐待确认 —— 单库内的唯一约束已经能完整表达订单幂等，额外加锁只是把数据库已有的能力搬到另一个会挂的组件上。
- 后果: + 语义由数据库保证，无额外中间件 / - 重试拉高单请求时延，且要求副作用可重复执行 / 缓解: 只对可判定的可重试错误重试，限定次数与总时长，重试次数进日志与指标。

## ADR-004 高峰保护在应用入口做准入，不靠扩连接池

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 2026-08 开票高峰连接池（Hikari 10→20）耗尽、服务假死约 6 分钟；根因不是池小，而是请求无上限地争抢有限连接（PG `max_connections=100`）。
- 决策: 在应用入口做准入控制（有界等待 + 超时快速失败返回 429），并固定连接池上限与语句/事务超时；不以扩池、加机器作为主要手段。依据: agent 推荐待确认 —— 连接是稀缺资源，扩池只是把排队从应用挪进数据库，排队时间从"可控的 200ms"变成"不可控的 6 分钟"。
- 后果: + 过载时数据库不被拖死，失败是明确且可预期的一类错误 / - 峰值会出现可见拒绝，需前端与运营配合话术 / 缓解: 开票前容量演练，拒绝量与排队深度进监控。

## ADR-005 报表库与交易库物理隔离

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 报表库与主库是同一实例的两个库，运营的大查询会抢 CPU/IO/连接，直接影响下单（`notes` 遗留判断）。
- 决策: 报表负载迁至独立 PG 实例，数据经逻辑复制获得（备选：定时导出），运营只连报表实例；主库收回面向运营的只读账号。依据: agent 推荐待确认 —— 同实例下换库名不隔离任何资源，"逻辑上分开"在故障面前等于没分。
- 后果: + 交易库资源可预期，运营跑坏查询不再影响下单 / - 多一个实例的备份、监控与升级责任 / 缓解: 复用现有备份脚本与监控项，报表库允许更长恢复时间（RTO 可放宽）。

## ADR-006 退款用本地状态机 + 渠道调用 + 补偿任务

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 退款入口是空壳，运营手工在库里改 `status`，月底对账经常对不上。退款涉及库存回补、渠道退款接口、退款单、对账口径四件事，此前因"以为改 status 就完了"一直拖延（`notes` 2026-08）。
- 决策: 以退款单为唯一事实源，按状态机推进（申请 → 渠道处理中 → 成功/失败 → 补偿），渠道调用与本地状态不做分布式事务，失败由补偿任务重试、必要时转人工。依据: agent 推荐待确认 —— 跨系统强一致不可得，支付渠道本身多为最终一致；与其追求"一次成功"，不如保证"失败一定被看见"。
- 后果: + 退款可查、可重试、可对账，消灭手工改库 / - 存在"处理中"中间态，需要运营理解并接受 / 缓解: 超时未决自动进人工待办，差异清单每日推送。

## ADR-007 金额、时间、状态的数据模型约定

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 金额用 `DECIMAL(18,2)` + `BigDecimal`（已正确，继续沿用）；状态是裸字符串无校验；`t_order` 无时间字段，导致按时段查询与对账都缺依据；本地 schema 为 H2 语法，与生产 PG 不一致。
- 决策: 金额一律 `DECIMAL(18,2)` / `BigDecimal`；时间统一 `timestamptz`，每张业务表带 `created_at` / `updated_at`；状态取值由 DB `CHECK` 约束与应用常量双重限定；schema 变更一律走迁移脚本。依据: agent 推荐待确认 —— 这三项是"能查、能对、能排障"的最小共同前提，缺任一项后面所有功能都要返工。
- 后果: + 时段查询/对账/排障有据，脏状态在入口被拦 / - 加 `CHECK` 前必须先清理历史脏值 / 缓解: 迁移前先跑一次性盘点脚本，列出所有非预期状态值。

## ADR-008 主链路以真实 PG 集成测试作为准入门槛

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 仓库无 `src/test`，改动靠人肉回归；过去一年 5 个已知问题里，4 个发生在数据库语义层（唯一索引冲突、行锁死锁、事务提交后的副作用）。
- 决策: 下单 / 退款 / 对账主链路用 Testcontainers 起真实 PG 做集成测试，作为 DoD 必过项；纯计算逻辑用单测补充，不追求覆盖率数字。依据: agent 推荐待确认 —— 被 H2 掩盖的方言与隔离级别差异，恰恰是过去故障的所在地。
- 后果: + 改主链路有据可依，敢在开票前发布 / - 本地需 Docker，测试比纯单测慢 / 缓解: 主链路收敛到一个测试类，控制在分钟级；慢测试单独 profile，不阻塞日常小改。

## ADR-009 schema 走版本化迁移，部署保留可回滚路径

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 生产 `application-prod.yml` 与建表语句都不在仓库，`schema.sql` 只有 H2 版本；发布方式是"改完传上去重启"，没有回滚路径。
- 决策: schema 用 Flyway 版本化并与代码同仓；部署维持 Docker Compose 单机，但每次发布必须带健康检查、保留上一版镜像、迁移遵守向后兼容纪律（先加列 → 双写/回填 → 再删列）。依据: agent 推荐待确认 —— 无运维、无灰度时，可回滚比零停机更现实。
- 后果: + 环境可重建、变更可追溯、回滚有据 / - 迁移纪律增加一次发布的步骤数 / 缓解: 迁移评审清单进 DoD「发布检查清单」。

## ADR-010 运营侧接口用最小鉴权，不自建账号体系

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 当前无任何鉴权；一旦上线退款与查询，任何能访问服务的人都能退钱、拉走全量订单与手机号。
- 决策: 运营侧接口走"网络层限制 + 单一静态凭据"的最小方案（内网/白名单 + 反向代理层校验），不自建账号、角色、会话体系；用户侧接口维持现状。依据: agent 推荐待确认 —— 运营只有 1~3 人，自建 IAM 的维护成本远高于它挡住的真实风险。
- 后果: + 一天内可上线，攻击面收敛到"内网可达 + 凭据泄露" / - 无法区分具体操作人，凭据轮换需手工 / 缓解: 操作日志记录来源 IP 与操作人参数（请求体自带），凭据轮换写进发布手册。

## ADR-011 可观测性取最小可用集，不买商业 APM

- 状态: Proposed (2026-10-24) · 替代: — · 被替代: —
- 背景: 目前只有应用日志，故障靠用户投诉发现——2026-08 假死 6 分钟无人提前知晓。
- 决策: 用 Actuator + Micrometer 暴露关键指标（下单成功率、延迟分位、连接池使用率、outbox 积压、对账差异数），Prometheus + Grafana + Alertmanager 与主服务同机 Compose 部署，告警推到工作群；不接入商业 APM。依据: agent 推荐待确认 —— 指标项与已知故障模式一一对应，单机三容器在 4C8G 上可承受，且不产生外部账单。
- 后果: + 故障先于用户被发现，容量演练有数据依据 / - 多三个容器要备份、升级、占内存 / 缓解: 与主服务同一 compose 管理，随主服务一起演练恢复；监控挂了不影响下单。
